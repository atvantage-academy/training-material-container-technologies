    Wissens-Check: Docker-Auffrischung

    Kubernetes orchestriert Container – und setzt voraus, dass Du weißt, was ein Container ist, woher er kommt und wo seine Daten bleiben. Diese sechzehn Fragen frischen die Docker-Grundlagen auf, auf denen der Kurs aufbaut.

    Es gibt keine Note und keine Auswertung im Kurs; die Antworten siehst nur Du. Lies bei jeder Antwort auch die Begründung – viele davon schlagen schon die Brücke zu Kubernetes.

    1. In Docker – und später in Kubernetes – begegnen Dir ständig zwei Begriffe: Image und Container.

      Was unterscheidet ein Image von einem Container?

      • Das Image ist eine unveränderliche Vorlage, der Container eine laufende Instanz davon.

      • Der Container ist die Vorlage, aus der beim Bauen die einzelnen Images abgeleitet werden.

      • Beide Begriffe meinen dasselbe – je nach Werkzeug heißt es mal Image, mal Container.

      • Ein Image liegt immer in der Registry, ein Container läuft immer lokal auf dem Rechner.

    2. Ein Container durchläuft während seines Lebens verschiedene Zustände.

      Was passiert mit einem Container, dessen Hauptprozess sich beendet?

      • Er stoppt und bleibt als beendeter Container stehen, bis ihn jemand entfernt.

      • Er läuft im Leerlauf weiter und wartet darauf, dass ihm neue Aufgaben zugewiesen werden.

      • Er wird von Docker sofort und ohne weitere Angaben automatisch neu gestartet.

      • Er wird automatisch gelöscht und hinterlässt keinerlei Spuren auf dem Rechner.

    3. Ein Container ändert zur Laufzeit Dateien, wird verworfen und neu aus dem Image erzeugt – die Änderungen sind weg.

      Welches Grundprinzip erklärt dieses Verhalten?

      • Die Schreibschicht eines Containers ist flüchtig – sie lebt und stirbt mit ihm.

      • Docker löscht nach jedem Lauf aus Sicherheitsgründen alle Dateien im Container.

      • Der Container hatte zu wenig Speicherplatz, um die Änderungen zu sichern.

      • Das zugrunde liegende Image war beschädigt und hat die Änderungen verworfen.

    4. Eine Webanwendung soll bei Lastspitzen einfach durch mehr Instanzen skaliert werden.

      Warum ist es dafür wichtig, dass die Anwendung zustandslos (stateless) ist?

      • Weil dann jede Instanz jede Anfrage bearbeiten kann, egal wie viele laufen.

      • Weil zustandslose Anwendungen spürbar weniger CPU und Arbeitsspeicher verbrauchen.

      • Weil eine zustandslose Anwendung dann gar keine Datenbank mehr braucht.

      • Weil zustandslose Container keine Umgebungsvariablen mehr benötigen.

    5. Eine Datenbank im Container speichert ihre Daten standardmäßig im Dateisystem des Containers.

      Wie stellst Du sicher, dass die Daten das Ersetzen oder Löschen des Containers überleben?

      • Mit einem Volume, das die Daten außerhalb des Containers speichert.

      • Mit einem Export vor jedem Löschen und einem Import nach dem Neustart.

      • Gar nicht nötig – Docker sichert die Daten vor dem Löschen automatisch.

      • Gar nicht nötig – die Daten bleiben im Image erhalten und sind wieder da.

    6. Ein Backend-Container muss eine Datenbank in einem anderen Container erreichen.

      Wie finden sich zwei Container in einem gemeinsamen Netzwerk?

      • Über den Container- bzw. Service-Namen, den ein eingebautes DNS auflöst.

      • Über die IP-Adresse des Hosts und die Ports, die nach außen veröffentlicht sind.

      • Gar nicht – Container sind grundsätzlich vollständig voneinander isoliert.

      • Über eine Shared-Memory-Verbindung, die Docker zwischen ihnen einrichtet.

    7. Die 12-Factor-App beschreibt bewährte Regeln für moderne Cloud-Anwendungen.

      Wie bekommt eine 12-Factor-App laut Faktor III („Config“) ihre Konfiguration?

      • Über Umgebungsvariablen, die beim Start von außen gesetzt werden.

      • Über eine Konfigurationsdatei, die je Umgebung ins Image gebaut wird.

      • Über Werte im Quellcode, die beim Kompilieren festgelegt werden.

      • Über eine zentrale Datenbank, die der Dienst bei jeder Anfrage abfragt.

    8. Nach der 12-Factor-App behandelt eine Anwendung ihre Logs auf eine bestimmte Weise (Faktor XI, „Logs“).

      Wohin schreibt eine containerisierte Anwendung ihre Logs?

      • Als Datenstrom nach stdout/stderr – die Plattform sammelt sie ein.

      • In eine rotierende Logdatei im Container, die regelmäßig abgeholt wird.

      • Direkt in eine fest verdrahtete, zentrale Log-Datenbank des Betriebs.

      • Nirgendwohin – Logs werden im Container aus Leistungsgründen abgeschaltet.

    9. Eine Anwendung nutzt eine Datenbank – in der Entwicklung eine lokale, in Produktion eine gehostete.

      Wie behandelt eine 12-Factor-App solche „Backing Services“ (Datenbanken, Caches, Queues)?

      • Als angehängte Ressourcen, per Konfiguration austauschbar, ohne Codeänderung.

      • Fest in den Code kompiliert, mit einer eigenen Programmversion für jede Datenbank.

      • Im selben Container wie die Anwendung, damit sie immer zusammen starten.

      • Ausschließlich lokal, damit die Anwendung ohne Netzwerkzugriff auskommt.

    10. Ein Container läuft, der Prozess ist gestartet – aber die Anwendung darin fährt noch hoch.

      Warum reicht „der Container läuft“ nicht aus, um Traffic auf ihn zu leiten?

      • Weil „gestartet“ nicht „bereit“ heißt – erst ein Health Check prüft das.

      • Es reicht – ist der Prozess gestartet, ist auch die Anwendung sofort bereit.

      • Weil ein laufender Container grundsätzlich niemals Traffic bekommt.

      • Weil Container generell keinen Netzwerkverkehr von außen annehmen.

    11. Ein Architekt überlegt, ob Anwendung und Datenbank in denselben Container gehören.

      Warum trennt man Anwendung und Datenbank üblicherweise in eigene Container?

      • Damit sich beide unabhängig skalieren, aktualisieren und neu starten lassen.

      • Weil ein Container technisch immer nur einen einzigen Prozess ausführen kann.

      • Weil der Speicher eines Containers nicht für zwei Dienste gleichzeitig reicht.

      • Gar nicht – alles in einen Container zu legen ist einfacher und üblich.

    12. Eine Anwendung besteht aus Frontend, Backend und einer rechenintensiven Bildverarbeitung. Nur die Bildverarbeitung ist unter Last überfordert.

      Welchen Vorteil bietet es, jede Komponente als eigenes Image und eigenen Container zu betreiben?

      • Du kannst gezielt nur die überlastete Komponente hochskalieren.

      • Alle drei teilen sich automatisch ein Basis-Image und sparen so Platz.

      • Die Anwendung wird durch die Aufteilung automatisch zustandslos.

      • Die Teile brauchen danach keine Netzwerkverbindung mehr zueinander.

    13. Ein Image wird einmal gebaut und dann unverändert durch Entwicklung, Test und Produktion gereicht – nur die Konfiguration ändert sich.

      Warum baut man nicht für jede Umgebung ein eigenes Image?

      • Weil so genau das getestete Artefakt ausgeliefert wird (Dev-Prod-Parität).

      • Weil Docker mehrere Images pro Projekt technisch nicht zulässt.

      • Weil ein Image je Umgebung automatisch größer ausfallen würde.

      • Weil sich ein Image nach dem Bauen nicht mehr verändern oder starten lässt.

    14. Ein Dockerfile nutzt einen Multi-Stage-Build: eine Stage zum Bauen und eine schlanke Stage für die Laufzeit.

      FROM maven:3.9 AS build
COPY . /app
RUN mvn -f /app/pom.xml package

FROM eclipse-temurin:21-jre
COPY --from=build /app/target/*.jar /app.jar
CMD ["java", "-jar", "/app.jar"]

      Welchen Vorteil hat das für das fertige Image?

      • Es enthält nur JRE und JAR – ohne Maven, Quellcode oder Zwischenstände.

      • Der Bau ist schneller, weil Docker beide Stages parallel ausführt.

      • Auf dem Zielsystem muss dadurch kein Java mehr installiert sein.

      • Es erlaubt, mehrere Anwendungen in einem einzigen Container zu betreiben.

    15. Ein Team pusht ein Image in eine Registry, ohne einen Tag anzugeben.

      Welchen Tag bekommt das Image – und warum ist das in der Praxis ein Problem?

      • latest – er wird bei jedem Push überschrieben, die Version bleibt unklar.

      • v1.0 – Docker liest die Version aus den Metadaten und zählt sie selbst hoch.

      • stable – Docker markiert erfolgreich gebaute Images als stabil.

      • Gar keinen – das Image ist danach in der Registry nicht auffindbar.

    16. In einer Container-Registry wird ein Image unter einem bestimmten Pfad gespeichert.

      Was ist ein „Repository“ im Zusammenhang mit einer Container-Registry?

      • Alle Versionen eines Images unter einem Namen, etwa mycompany/backend.

      • Ein Git-Repository mit Quellcode und Dockerfile, aus dem das Image gebaut wird.

      • Ein einzelner laufender Container auf einem Server der Registry.

      • Eine Sicherung aller Docker-Volumes eines Hosts in der Registry.
