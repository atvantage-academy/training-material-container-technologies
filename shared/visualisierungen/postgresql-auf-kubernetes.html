      PostgreSQL auf Kubernetes

      Datenbanken wie PostgreSQL sind zustandsbehaftet (stateful). Sie stellen andere Anforderungen als die zustandslosen Anwendungen, die Du bisher deployt hast – und Kubernetes hat dafür eine eigene Ressource: das StatefulSet.

      Warum ein StatefulSet?

      1. Stabile Identität

      Pods eines StatefulSets haben feste Namen – postgres-0, postgres-1 und so weiter. Sie bleiben auch nach Neustarts erhalten. Das braucht es für Replikation, Leader Election und die Kommunikation im Datenbank-Cluster.

      2. Feste Volume-Zuordnung

      Jeder Pod bekommt sein eigenes Persistent Volume: postgres-0 → PVC data-postgres-0, postgres-1 → PVC data-postgres-1. Keine Vermischung der Daten, Persistenz über Neustarts hinweg.

      3. Geordnetes Starten und Stoppen

      Pods starten nacheinander: postgres-0 → postgres-1 → postgres-2. Wichtig für Replikationsketten und einen sauberen Aufbau des Datenbank-Clusters.

      4. Skalierung mit Bedeutung

      Jeder Pod ist eine eigenständige Datenbankinstanz. Es gibt kein zufälliges Verteilen der Last wie bei einem Deployment.

      Warum sich zwei Pods kein Volume teilen dürfen

      PostgreSQL ist kein Shared-Disk-System. Nutzen mehrere Pods dasselbe Volume, drohen:

      • Datenkorruption
      • Konflikte im Write-Ahead Log (WAL)
      • fehlende Synchronisation zwischen den Prozessen
      • scheiternde Crash Recovery

      Regel: Ein PostgreSQL-Prozess = ein Datenverzeichnis = ein Volume.

      Und der Service?

      Ein Service bietet eine virtuelle IP und verteilt Traffic auf Pods. Er bietet aber keine stabile Identität je Pod und unterscheidet keine Rollen (Primary, Replica). Ein Service ersetzt also nicht die Identität eines StatefulSets.

      Für StatefulSets gibt es den Headless Service (clusterIP: None): Statt einer gemeinsamen IP erzeugt er DNS-Einträge je Pod, etwa postgres-0.postgres.

      Wann reicht ein Deployment mit PVC?

      Ein einfaches Deployment mit einem PersistentVolumeClaim reicht, wenn

      • nur eine einzige Datenbankinstanz gebraucht wird,
      • keine Replikation und kein Clustering nötig sind und
      • es um eine Entwicklungs- oder Testumgebung geht.

      Beispiel: PostgreSQL als StatefulSet

      Vier Ressourcen, die zusammen eine Datenbank ergeben. Das Beispiel nutzt ein Image, das auch unter OpenShift ohne Root-Rechte läuft (siehe unten).

      1. Secret

      Benutzer, Passwort und Datenbankname. Das Image erwartet die Variablen POSTGRESQL_USER, POSTGRESQL_PASSWORD und POSTGRESQL_DATABASE.

      apiVersion: v1
kind: Secret
metadata:
  name: postgres-secret
type: Opaque
stringData:
  POSTGRESQL_DATABASE: appdb
  POSTGRESQL_USER: appuser
  POSTGRESQL_PASSWORD: secretpassword
      2. Headless Service

      Für die DNS-Einträge je Pod – erzeugt Namen wie postgres-0.postgres.

      apiVersion: v1
kind: Service
metadata:
  name: postgres
spec:
  clusterIP: None
  selector:
    app: postgres
  ports:
    - port: 5432
      name: postgres
      3. Client Service

      Für die Anwendungen, die die Datenbank nutzen – eine stabile Adresse für alle Pods.

      apiVersion: v1
kind: Service
metadata:
  name: postgres-client
spec:
  selector:
    app: postgres
  ports:
    - port: 5432
      targetPort: 5432
      4. StatefulSet

      Der Kern: Pods mit fester Identität und je einem eigenen Volume aus volumeClaimTemplates.

      apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: quay.io/sclorg/postgresql-16-c9s
          ports:
            - containerPort: 5432
          envFrom:
            - secretRef:
                name: postgres-secret
          volumeMounts:
            - name: data
              mountPath: /var/lib/pgsql/data
          readinessProbe:
            exec:
              command:
                - pg_isready
                - -U
                - appuser
            initialDelaySeconds: 10
            periodSeconds: 5
          livenessProbe:
            exec:
              command:
                - pg_isready
                - -U
                - appuser
            initialDelaySeconds: 30
            periodSeconds: 10
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 5Gi
      Anwenden

      Stehen alle vier Ressourcen in einer Datei postgres.yaml (getrennt durch ---):

      # Kubernetes
kubectl apply -f postgres.yaml

      # OpenShift
oc apply -f postgres.yaml

      Besonderheit unter OpenShift

      Standard-Images von PostgreSQL (etwa postgres:17-alpine) laufen auf OpenShift oft nicht ohne Weiteres: Sie erwarten, als Root zu starten oder als fester Benutzer in ihr Datenverzeichnis zu schreiben. OpenShift startet Container aber mit einer zufälligen UID. Abhilfe:

      • ein OpenShift-taugliches Image wie quay.io/sclorg/postgresql-16-c9s
      • von Red Hat zertifizierte Images bzw. Operatoren aus dem OperatorHub

      Skalierung und Replikation

      Ein StatefulSet allein ergibt noch keine Hochverfügbarkeit. PostgreSQL braucht zusätzlich:

      • die Konfiguration von Primary und Replica(s)
      • Streaming Replication oder logische Replikation
      • Mechanismen für den Failover

      Das musst Du entweder selbst einrichten – oder einem Operator überlassen.

      Zusammenfassung

      • PostgreSQL braucht eine stabile Identität → StatefulSet.
      • Jeder Pod bekommt sein eigenes Volume.
      • Mehrere Pods auf einem PV → Datenkorruption.
      • Ein einfaches Deployment mit PVC nur für eine Instanz in Entwicklung und Test.
      • Produktion → Operator verwenden.
