      Health Checks mit Probes

      Kubernetes überwacht die Gesundheit von Containern mit Probes – regelmäßigen Prüfungen, die es selbst durchführt. Am Ergebnis entscheidet Kubernetes, ob ein Container Traffic bekommen darf, neu gestartet werden muss oder noch Zeit zum Starten braucht.

      Probes gehören zum Container, nicht zum Pod. Ein Pod mit mehreren Containern (etwa App und Sidecar) kann für jeden Container eigene Probes festlegen.

      Kubernetes ignoriert HEALTHCHECK aus dem Dockerfile. Die Anweisung wertet nur die Docker-Engine aus (etwa bei docker container run oder in Docker Compose). In Kubernetes stehen Health Checks immer als Probes in der Pod-Spezifikation.

      Die drei Probes

      Startup Probe

      Prüft: Ist der Container erfolgreich gestartet? Solange sie nicht erfolgreich war, laufen Liveness- und Readiness-Probe gar nicht erst.

      Bei Fehlschlag: Der Container wird neu gestartet (wie bei der Liveness-Probe).

      Wozu: Schutz für Container mit langer Startzeit. Ohne sie könnte die Liveness-Probe einen noch startenden Container für tot halten und neu starten – eine Endlosschleife.

      Liveness Probe

      Prüft: Lebt der Container noch? Schlägt sie fehl, hängt der Container, steckt in einem Deadlock oder kann sich nicht mehr erholen.

      Bei Fehlschlag: Kubernetes startet den Container neu (im selben Pod).

      Typisch: Deadlocks, Endlosschleifen, Speicherlecks, die den Prozess blockieren.

      Readiness Probe

      Prüft: Ist der Container bereit, Traffic zu empfangen? Ein Container kann leben, aber noch nicht bereit sein – etwa weil er Caches aufbaut oder auf die Datenbank wartet.

      Bei Fehlschlag: Der Pod wird aus dem Service genommen – er bekommt keinen Traffic mehr, wird aber nicht neu gestartet. Ist die Probe wieder erfolgreich, kommt er zurück.

      Zusammenspiel

      Liveness- und Readiness-Probe laufen parallel, während der ganzen Lebensdauer des Containers.

      Wie geprüft wird: die Mechanismen

      Mechanismus Beschreibung Beispiel
      httpGet HTTP-GET-Anfrage an einen Endpunkt. Erfolgreich bei Statuscode 200–399 Health-Endpunkt einer Webanwendung
      tcpSocket Prüft, ob ein TCP-Port Verbindungen annimmt Port einer Datenbank
      exec Führt einen Befehl im Container aus. Erfolgreich bei Exit-Code 0 pg_isready für PostgreSQL
      grpc Ruft den Standard-Health-Check von gRPC auf gRPC-Dienste

      Einstellungen

      livenessProbe:
  httpGet:
    path: /q/health/live
    port: 9000
  initialDelaySeconds: 5
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3
  successThreshold: 1
      Parameter Bedeutung Standard
      initialDelaySeconds Wartezeit nach dem Start des Containers bis zur ersten Prüfung 0
      periodSeconds Abstand zwischen zwei Prüfungen 10
      timeoutSeconds Wie lange auf eine Antwort gewartet wird 1
      failureThreshold Fehlschläge in Folge, bevor die Aktion ausgelöst wird 3
      successThreshold Erfolge in Folge, bevor der Container wieder als gesund gilt 1

      Nicht zu knapp, nicht zu großzügig. Zu kurze Werte für initialDelaySeconds und failureThreshold starten Container bei kurzer Last unnötig neu. Zu lange Werte verzögern das Erkennen echter Probleme.

      Beispiele für verschiedene Anwendungen

      Anwendung Startup Probe Liveness Probe Readiness Probe
      NGINX (statisches Frontend) – (startet schnell) httpGet auf /, Port 8080 httpGet auf /, Port 8080
      Quarkus-Backend httpGet auf /q/health/started, Port 9000 httpGet auf /q/health/live, Port 9000 httpGet auf /q/health/ready, Port 9000 (prüft auch die DB-Verbindung)
      Spring-Boot-Backend httpGet auf /actuator/health/liveness, Port 8080 httpGet auf /actuator/health/liveness, Port 8080 httpGet auf /actuator/health/readiness, Port 8080 (prüft auch die DB-Verbindung)
      PostgreSQL exec: pg_isready -U <user> exec: pg_isready -U <user> exec: pg_isready -U <user>

      NGINX

      NGINX startet sehr schnell, eine Startup-Probe ist nicht nötig. Liveness- und Readiness-Probe dürfen gleich sein – NGINX funktioniert oder eben nicht.

      Quarkus

      Quarkus bietet mit SmallRye Health eigene Endpunkte auf einem eigenen Management-Port (9000). Die Readiness-Probe prüft zusätzlich Abhängigkeiten wie die Verbindung zur Datenbank.

      Spring Boot

      Spring Boot bietet über Actuator ähnliche Endpunkte. Seit Version 2.3 gibt es Liveness und Readiness als eigene Health Groups.

      PostgreSQL

      PostgreSQL hat keine HTTP-Endpunkte. Deshalb prüft exec mit dem mitgelieferten Werkzeug pg_isready.
