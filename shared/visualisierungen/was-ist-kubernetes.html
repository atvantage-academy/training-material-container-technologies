      Was ist Kubernetes?

      Kubernetes (oft als K8s abgekürzt) ist eine Open-Source-Plattform zur Container-Orchestrierung. Ursprünglich bei Google entwickelt und 2014 als Open-Source-Projekt veröffentlicht, wird es heute von der Cloud Native Computing Foundation (CNCF) verwaltet.

      Kubernetes automatisiert die Bereitstellung, Skalierung und Verwaltung von containerisierten Anwendungen über einen Verbund von Maschinen hinweg – den Cluster.

      Der Cluster im Überblick

      Ein Kubernetes-Cluster besteht aus zwei Arten von Maschinen:

      Control Plane

      Verwaltet den Cluster, plant Workloads und überwacht den Zustand. Früher auch „Master“ genannt.

      Worker Nodes

      Führen die eigentlichen Container aus – verpackt in Pods.

      Klapp die Bausteine auf – erst die der Control Plane, dann die der Worker Nodes.

      Control Plane

      API Server

      Die zentrale Schnittstelle des Clusters. Jede Interaktion – ob über kubectl, oc, die Web Console oder andere Komponenten – läuft über den API Server. Er validiert und verarbeitet Anfragen und schreibt den gewünschten Zustand in etcd.

      etcd

      Von /etc + distributed – ein „verteiltes Konfigurationsverzeichnis“. Ein verteilter Key-Value-Store, der den gesamten Cluster-Zustand persistent speichert: Deployments, Pods, ConfigMaps, Secrets und so weiter.

      Nur der API Server greift direkt auf etcd zu. Fällt etcd aus, ist der Cluster effektiv blind.

      Scheduler

      Beobachtet neu erstellte Pods, die noch keinem Knoten zugewiesen sind, und entscheidet anhand von Ressourcen, Constraints und Affinitätsregeln, auf welchem Worker Node ein Pod platziert wird.

      Controller Manager

      Führt eine Sammlung von Controllern aus, die kontinuierlich den Ist-Zustand des Clusters mit dem Soll-Zustand abgleichen. Beispiele: Der ReplicaSet-Controller stellt sicher, dass die gewünschte Anzahl Pods läuft; der Node-Controller erkennt ausgefallene Knoten.

      Worker Nodes

      kubelet

      Der Node-Agent – der Prozess, über den sich ein Knoten steuern lässt. Der kubelet läuft auf jedem Worker Node und startet die vom Scheduler zugewiesenen Pods, überwacht sie und startet sie bei Bedarf neu. Er spricht mit dem API Server, meldet den Zustand des Knotens und seiner Pods und steuert die Container-Runtime.

      kube-proxy

      Der Netzwerk-Proxy auf jedem Knoten. Er setzt die Service-Abstraktion von Kubernetes um, indem er Netzwerkregeln (iptables/IPVS) verwaltet, die eingehenden Traffic an die richtigen Pods weiterleiten – auch über Knotengrenzen hinweg.

      Container-Runtime

      Die Software, die Container tatsächlich startet und ausführt. Kubernetes unterstützt jede Runtime, die das Container Runtime Interface (CRI) implementiert, zum Beispiel containerd oder CRI-O (von OpenShift verwendet).

      Pod

      Die kleinste bereitstellbare Einheit. Ein Pod enthält einen oder mehrere Container, die sich einen Netzwerk-Namespace teilen und über localhost miteinander sprechen können. Pods legt man in der Regel nicht direkt an, sondern lässt sie von einem Deployment verwalten – mehr dazu unter Kubernetes-Ressourcen.

      Die Kommandozeile: kubectl

      Mit einem Kubernetes-Cluster sprichst Du über das Kommandozeilenwerkzeug kubectl. Damit erstellst, siehst, änderst und löschst Du Ressourcen. Alle Befehle gehen über den API Server.

      # Pods im eingestellten Namespace anzeigen
kubectl get pods

# Ressourcen aus einer YAML-Datei anlegen oder aktualisieren
kubectl apply -f deployment.yaml

# Logs eines Pods anzeigen
kubectl logs <pod-name>

      Eine Übersicht der wichtigsten Befehle – für kubectl und oc nebeneinander – steht im Spickzettel: kubectl und oc. Kubernetes verwaltet Anwendungen über deklarative Ressourcen wie Pods, Deployments, Services und ConfigMaps; sie erklärt die Seite Kubernetes-Ressourcen.

      Docker und Kubernetes – wofür was?

      Docker und Kubernetes lösen unterschiedliche Probleme und ergänzen sich.

      Docker (inkl. Compose) Kubernetes
      Zweck Container bauen und lokal ausführen Container über mehrere Maschinen hinweg orchestrieren
      Skalierung Manuell (zum Beispiel replicas in Compose) Automatisch (Horizontal Pod Autoscaler, ReplicaSets)
      Hochverfügbarkeit Nicht vorgesehen – fällt der Host aus, ist alles weg Pods werden automatisch auf gesunde Knoten verschoben
      Rollouts Manuell, mit Downtime Rolling Updates, Blue-Green-Deployments, Canary Releases
      Netzwerk Einfaches Bridge-Netzwerk Cluster-weites Netzwerk mit Service Discovery und DNS
      Konfiguration .env-Dateien, docker-compose.yml ConfigMaps, Secrets, deklarative YAML-Manifeste
      Health Checks HEALTHCHECK im Dockerfile (begrenzt) Startup-, Liveness- und Readiness-Probes mit automatischem Neustart
      Speicher Bind Mounts, Volumes Persistent Volumes mit StorageClasses und dynamischer Provisionierung
      Geeignet für Entwicklung, einfache Deployments Produktion, Microservices, hohe Verfügbarkeit

      Wann Docker (Compose)?

      • Lokale Entwicklung – schnell einen Stack aus mehreren Services starten
      • Einfache Deployments – ein einzelner Host, keine Hochverfügbarkeit nötig

      Wann Kubernetes?

      • Produktion – wenn Hochverfügbarkeit, automatische Skalierung und Selbstheilung gebraucht werden
      • Microservices – viele Services, die unabhängig deployt und skaliert werden
      • Mehrere Teams – Namespaces, RBAC und Resource Quotas für organisatorische Trennung
      • Hybrid und Multi-Cloud – eine einheitliche Plattform über verschiedene Infrastrukturen hinweg

      Zusammenspiel

      Docker und Kubernetes sind keine Konkurrenten:

      1. Docker baut die Container-Images (Dockerfile → docker image build).
      2. Die Images werden in eine Registry gepusht (Docker Hub, ghcr.io und andere).
      3. Kubernetes zieht die Images und orchestriert ihre Ausführung im Cluster.

      Kubernetes braucht die Docker-Engine nicht. Seit Version 1.24 setzt Kubernetes auf containerd oder CRI-O als Runtime. Docker-Images laufen trotzdem weiter, denn sie entsprechen dem OCI-Standard.

      Kubernetes lokal ausprobieren

      Mit Minikube startest Du einen lokalen Kubernetes-Cluster auf Deinem Rechner – ideal zum Lernen und Experimentieren. Minikube läuft unter Linux, macOS und Windows und unterstützt verschiedene Virtualisierungs-Backends (Docker, VirtualBox, Hyper-V und andere). Wie Du es für die Schulung einrichtest, steht unter Minikube für die Schulung einrichten.

      # Lokalen Cluster starten
minikube start

      # Die Knoten des Clusters anzeigen
kubectl get nodes
