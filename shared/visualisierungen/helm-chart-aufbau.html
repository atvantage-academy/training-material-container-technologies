Aufbau eines Helm Charts

    Aufbau eines Helm Charts

    Ein Helm Chart ist ein Verzeichnis mit fester Struktur. Das sind alle Dateien und Verzeichnisse, die ein Chart enthalten kann – erforderlich ist nur Chart.yaml. Was ein Chart ist und wozu es dient, steht unter Helm Charts.

    my-app/
├── Chart.yaml            # Metadaten und Abhängigkeiten (erforderlich)
├── Chart.lock            # Exakte Versionen der aufgelösten Dependencies
├── values.yaml           # Standardwerte (beim Installieren überschreibbar)
├── values.schema.json    # JSON Schema zur Prüfung der Values
├── .helmignore           # Dateien, die beim Verpacken ignoriert werden
├── LICENSE               # Lizenz des Charts
├── README.md             # Dokumentation des Charts (erscheint auf Artifact Hub)
├── templates/            # Kubernetes-Manifeste als Go-Templates
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── configmap.yaml
│   ├── secret.yaml
│   ├── ingress.yaml
│   ├── _helpers.tpl      # Wiederverwendbare Template-Bausteine (keine Ausgabe)
│   ├── NOTES.txt         # Hinweistext nach Install/Upgrade (Go-Template)
│   └── tests/            # Helm-Tests (Pods, die nach dem Install laufen)
│       └── test-connection.yaml
├── charts/               # Subcharts (Dependencies, geladen oder lokal)
│   └── postgresql/
└── crds/                 # Custom Resource Definitions (vor den Templates installiert)
    └── my-crd.yaml

    Chart.yaml (erforderlich)

    Die Metadaten des Charts – Name, Version, Abhängigkeiten:

    apiVersion: v2              # v2 = Helm 3 (v1 = Helm 2, veraltet)
name: my-app
version: 1.0.0              # Version des Charts selbst (SemVer)
appVersion: "2.3.1"         # Version der verpackten Anwendung
description: Recipes Backend für Kubernetes
type: application           # "application" oder "library"
dependencies:
  - name: postgresql
    version: "~15.2"
    repository: oci://registry-1.docker.io/bitnamicharts
    condition: postgresql.enabled
    Feld Bedeutung
    version Die Version des Charts – gilt bei helm package und in der Registry
    appVersion Die Version der Anwendung, die das Chart installiert (rein informativ)
    type application (installierbar) oder library (nur als Dependency nutzbar, erzeugt keine eigenen Ressourcen)
    dependencies Andere Charts, die automatisch mitinstalliert werden

    values.yaml

    Die Standardwerte, die beim Installieren überschrieben werden können:

    image:
  repository: ralfueberfuhr/recipes-backend
  tag: latest-dev
replicas: 1
service:
  port: 8080

    In den Templates greifst Du darauf mit {{ .Values.image.tag }} zu.

    values.schema.json

    Ein optionales JSON Schema, das die Values bei helm install prüft. Damit lässt sich etwa erzwingen, dass replicas eine Zahl ist oder image.tag gesetzt sein muss:

    {
  "$schema": "https://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["image"],
  "properties": {
    "replicas": { "type": "integer", "minimum": 1 },
    "image": {
      "type": "object",
      "required": ["repository", "tag"],
      "properties": {
        "repository": { "type": "string" },
        "tag": { "type": "string" }
      }
    }
  }
}

    templates/

    Kubernetes-Manifeste als Go-Templates. Jede .yaml-Datei in diesem Verzeichnis wird gerendert und auf den Cluster angewendet. Einige Dateien haben eine Sonderrolle:

    NOTES.txt

    Text, der nach helm install und helm upgrade in der Konsole erscheint. Er unterstützt Go-Templating und zeigt typischerweise die nächsten Schritte:

    Dein Release {{ .Release.Name }} wurde installiert!

So erreichst Du die Anwendung:
  export URL=$(kubectl get route {{ .Release.Name }} -o jsonpath='{.spec.host}')
  echo "Öffne https://$URL"
    _helpers.tpl

    Dateien, deren Name mit einem Unterstrich (_) beginnt, erzeugen kein Manifest. Sie enthalten wiederverwendbare Template-Funktionen, die andere Templates mit {{ include }} aufrufen:

    {{- define "my-app.fullname" -}}
{{ .Release.Name }}-{{ .Chart.Name }}
{{- end -}}

{{- define "my-app.labels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}
app.kubernetes.io/instance: {{ .Release.Name }}
app.kubernetes.io/version: {{ .Chart.AppVersion }}
{{- end -}}

    Verwendet in einem Template:

    metadata:
  name: {{ include "my-app.fullname" . }}
  labels:
    {{- include "my-app.labels" . | nindent 4 }}
    tests/

    Pods mit der Annotation helm.sh/hook: test, die nach der Installation mit helm test my-release laufen:

    apiVersion: v1
kind: Pod
metadata:
  name: {{ .Release.Name }}-test
  annotations:
    "helm.sh/hook": test
spec:
  containers:
    - name: curl-test
      image: curlimages/curl
      command: ['curl', '--fail', 'http://{{ .Release.Name }}:8080/health']
  restartPolicy: Never

    Typische Einsätze: eine HTTP-Anfrage an den Service, die Verbindung zur Datenbank prüfen, ein Smoke-Test.

    charts/

    Subcharts, also Dependencies. helm dependency update lädt sie anhand der Dependencies in Chart.yaml herunter; alternativ liegen sie als Verzeichnisse von Hand darin.

    crds/ – Custom Resource Definitions

    Kubernetes kennt von Haus aus Ressourcen wie Pod, Service oder Deployment. Eine CRD erweitert die Kubernetes-API um eigene Ressourcentypen. Ein Datenbank-Operator könnte etwa den Typ PostgresCluster einführen – danach steht in YAML-Manifesten kind: PostgresCluster, als wäre es eine eingebaute Ressource.

    CRDs behandelt Helm besonders vorsichtig. Sie werden vor allen Templates installiert, bei helm upgrade aber nicht aktualisiert – CRD-Updates erfolgen von Hand. Bei helm uninstall werden sie nicht gelöscht: Ein versehentliches Deinstallieren soll nicht alle Custom Resources im Cluster mitreißen.

    Die CRD im Chart

    Ein Chart für einen Monitoring-Operator bringt eine CRD mit, die den Typ MonitoringRule einführt:

    # crds/monitoring-rule-crd.yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: monitoringrules.example.com
spec:
  group: example.com
  names:
    kind: MonitoringRule
    plural: monitoringrules
    singular: monitoringrule
    shortNames:
      - mr
  scope: Namespaced
  versions:
    - name: v1
      served: true
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                metric:
                  type: string
                threshold:
                  type: integer
    Eine Instanz im Template

    Ist das Chart installiert, kennt der Cluster den neuen Typ. In templates/ lassen sich dann konkrete Instanzen davon anlegen:

    # templates/alert-rule.yaml
apiVersion: example.com/v1
kind: MonitoringRule
metadata:
  name: high-cpu-alert
spec:
  metric: cpu_usage_percent
  threshold: 90

    Warum crds/ und nicht templates/? Helm muss die CRD erst registrieren, bevor Templates Instanzen davon anlegen können. Dateien in crds/ werden deshalb immer zuerst angewendet – und sie werden nicht als Template gerendert.

    .helmignore

    Funktioniert wie .gitignore: Dateien und Verzeichnisse, die bei helm package nicht ins Archiv sollen.

    .git/
*.swp
*.tmp
.idea/
.vscode/

    Chart.lock

    Entsteht automatisch bei helm dependency update. Enthält die exakt aufgelösten Versionen aller Dependencies – vergleichbar mit package-lock.json bei npm. Gehört ins Git-Repository, damit alle im Team dieselben Versionen bekommen.
