      Helm Charts

      Helm ist der Paketmanager für Kubernetes. So wie apt für Debian oder npm für Node.js bündelt Helm Kubernetes-Ressourcen zu wiederverwendbaren Paketen – den Charts.

      Warum Helm?

      Wer eine Anwendung auf Kubernetes deployt, schreibt mehrere YAML-Manifeste: Deployment, Service, ConfigMap, Secret, Route oder Ingress, PersistentVolumeClaim. Schnell kommen diese Fragen:

      Redundanz

      Dieselbe Anwendung läuft in Dev, Staging und Prod – mit leicht anderer Konfiguration. Man pflegt drei Sätze fast gleicher YAML-Dateien.

      Versionierung

      Welche Fassung der Manifeste läuft gerade in Produktion? Für ein Rollback müssen erst die richtigen YAML-Dateien wiedergefunden werden.

      Abhängigkeiten

      Die Anwendung braucht eine Datenbank. Beide müssen zusammen deployt werden – in der richtigen Reihenfolge, mit abgestimmter Konfiguration.

      Weitergabe

      Ein Team will seine Anwendung anderen bereitstellen – und müsste dafür lose YAML-Dateien plus Installationsanleitung verschicken.

      Was Helm daran ändert

      Ohne Helm Mit Helm
      Viele lose YAML-Dateien Ein Chart = ein Paket
      Werte sind fest eingetragen Parametrisiert über values.yaml
      Kein Überblick über Installationen helm list zeigt die installierten Releases
      Rollback = YAML von Hand tauschen helm rollback auf eine frühere Revision
      Kein Paketformat Charts sind teilbar, versioniert, signierbar
      Abhängigkeiten von Hand Chart.yaml deklariert Dependencies

      Die Kernbegriffe

      Chart

      Ein Chart ist ein Paket aus Templates und Standardwerten, das eine Anwendung beschreibt. Es ist ein Verzeichnis mit fester Struktur:

      my-app/
├── Chart.yaml            # Metadaten und Abhängigkeiten (erforderlich)
├── Chart.lock            # Exakte Versionen der aufgelösten Dependencies
├── values.yaml           # Standardwerte (beim Installieren überschreibbar)
├── values.schema.json    # JSON Schema zur Prüfung der Values
├── .helmignore           # Dateien, die beim Verpacken ignoriert werden
├── LICENSE               # Lizenz des Charts
├── README.md             # Dokumentation des Charts
├── templates/            # Kubernetes-Manifeste als Go-Templates
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── _helpers.tpl      # Wiederverwendbare Template-Bausteine
│   ├── NOTES.txt         # Hinweistext nach Install/Upgrade
│   └── tests/            # Helm-Tests
├── charts/               # Subcharts (Dependencies)
└── crds/                 # Custom Resource Definitions

      Jede Datei im Einzelnen: Aufbau eines Helm Charts.

      Release

      Ein Release ist eine konkrete Installation eines Charts in einem Cluster. Dasselbe Chart lässt sich mehrfach installieren – etwa als my-app-dev und my-app-prod. Jedes Release hat seine eigene Revisionshistorie für Upgrades und Rollbacks.

      Values

      Values parametrisieren ein Chart. Sie stehen in values.yaml und lassen sich beim Installieren überschreiben.

      # values.yaml
image:
  repository: ralfueberfuhr/recipes-backend
  tag: latest-dev
replicas: 1

      # templates/deployment.yaml (Auszug)
spec:
  replicas: {{ .Values.replicas }}
  template:
    spec:
      containers:
        - name: backend
          image: {{ .Values.image.repository }}:{{ .Values.image.tag }}

      # Einen Wert beim Installieren überschreiben
helm install my-release ./my-app --set replicas=3

      # Oder eine ganze Datei mit Werten mitgeben
helm install my-release ./my-app -f prod-values.yaml
      Repository

      Charts werden auf zwei Wegen verteilt: über ein klassisches Chart-Repository oder über eine OCI-Registry. Den Vergleich zeigt der nächste Abschnitt.

      Repository: klassisch oder OCI

      Klassisches Chart-Repository (Legacy)

      Ein HTTP-Server, der eine index.yaml mit den verfügbaren Charts bereitstellt. Dafür braucht es einen eigenen Server (ChartMuseum, GitHub Pages, Nexus o. Ä.).

      Chart Repository
├── index.yaml
├── my-app-1.0.0.tgz
├── my-app-1.1.0.tgz
└── postgresql-15.2.0.tgz

      Viele bestehende Charts werden noch so verteilt.

      OCI-Registry (ab Helm 3.8 – empfohlen)

      Charts liegen direkt in einer Container-Registry – derselben, die auch die Images hält (Docker Hub, GitHub Container Registry, Quay.io, Harbor, ACR, ECR …). Das ist der empfohlene Weg für neue Setups und löst das klassische Modell langfristig ab.

      Was heißt „OCI“ in diesem Zusammenhang?

      OCI steht für Open Container Initiative – eine Organisation, die offene Standards für Container-Formate und Registries festlegt. Dazu gehört die OCI Distribution Specification: ein Protokoll, über das Registries beliebige Artefakte speichern und verteilen, nicht nur Container-Images.

      Helm nutzt genau dieses Protokoll: Charts werden als OCI-Artefakte in jeder OCI-kompatiblen Registry gespeichert.

      • OCI als Organisation legt Standards fest (Image-Format, Runtime, Distribution).
      • Die OCI Distribution Spec ist das Protokoll, das Helm nutzt.
      • Ein Chart ist kein Container-Image, wird aber über dasselbe Protokoll und in derselben Registry gespeichert.
      • Es braucht keine eigene Infrastruktur für Charts – die vorhandene Registry reicht.
      Klassisches Repository OCI-Registry
      Protokoll Eigenes Helm-Protokoll (HTTP + index.yaml) OCI Distribution Spec
      Infrastruktur Eigener Chart-Server nötig Vorhandene Container-Registry
      Suche helm search repo Oberfläche der Registry oder Artifact Hub
      Helm-Version Alle Ab 3.8 (stabil)
      Status Legacy – funktioniert, aber nicht mehr empfohlen Empfohlen für neue Setups

      Helm und OpenShift

      OpenShift unterstützt Helm vollständig:

      • Die Helm-CLI funktioniert genauso wie mit jedem anderen Kubernetes (helm install, helm upgrade …).
      • Die Web Console zeigt installierte Helm-Releases an, und ihr Katalog listet Charts aus eingerichteten Repositories. Im Kurs arbeitest Du trotzdem nur mit der Kommandozeile.
      • Die integrierte Registry unterstützt OCI-Artefakte und damit Helm Charts.

      Helm-Templates dürfen OpenShift-eigene Ressourcen wie Routes enthalten – es sind gewöhnliche Kubernetes-YAML-Templates.

      Stärken und Herausforderungen

      Stärken

      • Wiederverwendbarkeit: Ein Chart, viele Umgebungen – Unterschiede nur in den Values.
      • Versionierung und Rollback: Jedes Release hat eine Revisionshistorie; zurück geht es mit einem Befehl.
      • Abhängigkeiten: Charts deklarieren andere Charts als Dependency (etwa ein Backend-Chart, das ein PostgreSQL-Chart braucht).
      • Ökosystem: Tausende öffentlicher Charts (etwa auf Artifact Hub) für Standardsoftware – PostgreSQL, Redis, NGINX, Prometheus.
      • Standardisierung: Ein einheitliches Format, das Teams und Cluster-Admins verstehen.

      Herausforderungen

      • Lernkurve: Go-Templating ({{ if }}, {{ range }}, {{ include }}) ist mächtig, die Syntax aber gewöhnungsbedürftig – besonders bei Verschachtelung und Leerraum.
      • Fehlersuche: Fehler in Templates erzeugen oft kryptische Meldungen. helm template und helm lint helfen, aber es bleibt aufwendiger als bei reinem YAML.
      • Große Charts: Umbrella-Charts mit vielen Subcharts werden schnell unübersichtlich; Values über mehrere Ebenen sind fehleranfällig.
      • Kein GitOps von Haus aus: Helm arbeitet imperativ (helm install, helm upgrade). Für GitOps braucht es Werkzeuge wie Argo CD oder Flux.
      • Drift: Ändert jemand nach helm install Ressourcen von Hand (kubectl edit, oc edit), weicht der Cluster vom Chart ab. Helm merkt das erst beim nächsten helm upgrade.

      Erste Schritte

      Voraussetzung: Zugang zum Cluster (kubeconfig)

      Helm bringt keinen eigenen Cluster-Zugang mit. Es nutzt die kubeconfig – dieselbe Datei, die kubectl liest und die alle Kubernetes-Werkzeuge übernommen haben (oc, helm, Lens, k9s …).

      In der Praxis heißt das: Wer mit kubectl arbeiten kann oder sich mit oc login angemeldet hat, kann Helm sofort nutzen. oc login schreibt die Zugangsdaten nach ~/.kube/config, und Helm liest sie von dort.

      # Nach dem Login am Cluster …
oc login https://api.cluster.example.com:6443

      # … funktioniert Helm sofort
helm list

      Die Umgebungsvariable KUBECONFIG

      KUBECONFIG ist eine Konvention von kubectl, die Helm übernommen hat. Du brauchst sie nur, wenn die kubeconfig nicht unter ~/.kube/config liegt:

      # Nur nötig, wenn die kubeconfig woanders liegt
export KUBECONFIG=/pfad/zu/meiner/kubeconfig.yaml

      Mehrere Cluster? Eine kubeconfig kann mehrere Kontexte enthalten; gewechselt wird mit kubectl config use-context <name>. Alternativ führt KUBECONFIG=/pfad/a:/pfad/b (mit Doppelpunkt getrennt) mehrere Dateien zusammen.

      Aufbau der kubeconfig

      Die Datei hat drei Bereiche – Cluster, Benutzer und die Kontexte, die beides verbinden:

      apiVersion: v1
kind: Config
current-context: my-cluster            # Aktiver Kontext

clusters:                              # Verbindungen zu Clustern
  - name: my-cluster
    cluster:
      server: https://api.cluster.example.com:6443
      certificate-authority-data: LS0t...   # CA-Zertifikat (Base64)

users:                                 # Zugangsdaten
  - name: developer
    user:
      token: sha256~abc123...          # Bearer Token (etwa von oc login)

contexts:                              # Cluster + Benutzer + Namespace
  - name: my-cluster
    context:
      cluster: my-cluster
      user: developer
      namespace: my-project
      • clusters – Adressen und Zertifikate der Kubernetes- bzw. OpenShift-Cluster
      • users – Anmeldung (Token, Client-Zertifikat oder OIDC)
      • contexts – verbinden Cluster, Benutzer und optional einen Standard-Namespace

      1. Helm installieren

      In der bereitgestellten Schulungsumgebung ist Helm schon da. Auf dem eigenen Rechner:

      macOS 
      brew install helm
      Windows (Git Bash) 
      winget install Helm.Helm
      Linux 
      sudo snap install helm --classic

      Alternativ das Programm von den Helm-Releases herunterladen.

      2. Ein Chart anlegen

      helm create my-app

      Das erzeugt ein vollständiges Chart mit Beispiel-Templates. Für den Einstieg ersetzt Du die Templates durch Deine eigenen YAML-Manifeste und parametrisierst sie Schritt für Schritt.

      3. Das Chart prüfen, ohne es zu installieren

      # Templates rendern und ansehen
helm template my-release ./my-app

      # Mit eigenen Values rendern
helm template my-release ./my-app -f prod-values.yaml

      # Das Chart auf Fehler prüfen
helm lint ./my-app

      4. Das Chart installieren

      helm install my-release ./my-app

      5. Das Release verwalten

      # Installierte Releases auflisten
helm list

      # Werte ändern und upgraden
helm upgrade my-release ./my-app --set replicas=3

      # Auf Revision 1 zurückrollen
helm rollback my-release 1

      # Das Release entfernen
helm uninstall my-release

      Alle Befehle auf einen Blick: Spickzettel: Helm.
