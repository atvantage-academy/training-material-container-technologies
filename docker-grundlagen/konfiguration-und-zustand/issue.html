    Eine Datenbank konfigurieren

    Als Entwickler möchte ich eine Datenbank einrichten, ohne ihr Image anzufassen, damit dasselbe Artefakt in Entwicklung, Test und Produktion unterschiedlich arbeiten kann.

    Lernziele

    Du…

    • nutzt Umgebungsvariablen, um einen Container umgebungsspezifisch zu konfigurieren.
    • richtest eine PostgreSQL-Datenbank ein.
    • überprüfst die Log-Ausgabe eines Containers, um einen Fehler zu finden.
    • legst ein Volume an und weist nach, dass Daten darin das Löschen des Containers überleben.

    Definition of Done

    • In einem Container läuft eine Datenbank.
    • Die Tabellen sind angelegt und im Container mit psql abrufbar.
    • Die Datenbank ist auch außerhalb des Containers erreichbar.
    • Die Daten der Datenbank sind auch nach Löschen und Neuerzeugen des Containers vorhanden.

    Arbeitsschritte

    Einen Container ohne Konfiguration starten

    docker container run -d --name meine-db postgres:16

    Der Container läuft nicht. Sieh nach, warum:

    docker container logs meine-db

    Hinweis: Die Meldung sagt Dir genau, welche Angabe fehlt. docker container logs ist ab jetzt Dein erster Griff, wenn etwas nicht tut.

    Räum den gescheiterten Versuch weg – den Namen brauchst Du gleich wieder.

    Umgebungsvariablen setzen

    Jede Angabe kommt mit einem eigenen -e von außen dazu:

    docker container run -d \
  --name meine-db \
  -p 5432:5432 \
  -e POSTGRES_DB=helloworld \
  -e POSTGRES_USER=kurs \
  -e POSTGRES_PASSWORD=geheim \
  postgres:16

    Prüfe in der Log-Ausgabe, dass die Datenbank bereit ist:

    docker container logs meine-db

    Hinweis: Woher kommen die Namen POSTGRES_DB, POSTGRES_USER und POSTGRES_PASSWORD? Sieh im Datenblatt des Images auf Docker Hub nach. Merk Dir, wo diese Information steht – bei jedem anderen Image wirst Du sie dort wieder suchen.

    Ein Schema mit Tabellen anlegen

    Das Schema gehört nicht in einen Befehl, sondern in eine Datei. Leg auf Deinem Rechner schema.sql an:

    CREATE TABLE gruss (
  id   SERIAL PRIMARY KEY,
  text TEXT NOT NULL
);

INSERT INTO gruss (text)
VALUES ('Hallo Welt'), ('Hello World'), ('Bonjour le monde');

    Das Image führt beim ersten Start jede .sql-Datei aus, die in /docker-entrypoint-initdb.d/ liegt. Reich Deine Datei also dorthin hinein – der Container von eben hat seine Datenbank schon angelegt, also weg damit und neu:

    docker container run -d \
  --name meine-db \
  -p 5432:5432 \
  -e POSTGRES_DB=helloworld \
  -e POSTGRES_USER=kurs \
  -e POSTGRES_PASSWORD=geheim \
  -v "$(pwd)/schema.sql":/docker-entrypoint-initdb.d/1-schema.sql \
  postgres:16

    Zum Prüfen – und nur dafür – fragst Du die Datenbank mit psql ab, von innen:

    docker container exec meine-db psql -U kurs -d helloworld -c "SELECT * FROM gruss"

    Nachsehen, ob die Datenbank auch von außen erreichbar ist

    psql im Container beweist nur, dass die Datenbank sich selbst erreicht. Ob der veröffentlichte Port wirklich auf Deinem Rechner liegt, zeigt ein Blick auf die offenen Ports – außerhalb von Docker:

    Linux:

    ss -ltn | grep 5432

    macOS:

    netstat -an | grep LISTEN | grep 5432

    Windows:

    netstat -ano | find "5432"

    Hinweis: Eine Zeile mit LISTEN auf Port 5432 heißt: Dein Rechner nimmt dort Verbindungen an und reicht sie in den Container weiter. Mach die Gegenprobe – stopp den Container und sieh noch einmal nach. Dann ist die Zeile weg.

    Die Daten der Datenbank außerhalb des Containers speichern

    Bisher liegen die Daten im Container. Leg einen Ablageort an, der ihn überdauert:

    docker volume create kurs-daten

    Erzeuge die Datenbank neu – mit dem Volume und mit PGDATA:

    docker container run -d \
  --name meine-db \
  -p 5432:5432 \
  -e POSTGRES_DB=helloworld \
  -e POSTGRES_USER=kurs \
  -e POSTGRES_PASSWORD=geheim \
  -e PGDATA=/var/lib/postgresql/data/pgdata \
  -v kurs-daten:/var/lib/postgresql/data \
  -v "$(pwd)/schema.sql":/docker-entrypoint-initdb.d/1-schema.sql \
  postgres:16

    Hinweis: PGDATA sagt dem Image, wo es seine Dateien ablegen soll. Ohne die Angabe hängt das Verzeichnis von der Image-Version ab – mit ihr liegt es immer an derselben Stelle unter Deinem Volume.

    Jetzt die Probe: Lösch den Container und erzeuge ihn neu – mit denselben Angaben wie eben. Frag danach wieder die Tabelle ab.

    Hinweis: Überleg Dir vorher, was Du erwartest. Zwei Dinge sind zu beobachten: ob Deine Zeilen noch da sind – und ob schema.sql ein zweites Mal gelaufen ist.

    Optional: Das Passwort aus einer Datei lesen

    Das Passwort steht bisher im Befehl – und damit in Deiner Shell-History und in docker container inspect. Das Image kennt zu seinen POSTGRES_*-Variablen jeweils eine Schwester mit dem Zusatz _FILE: Sie enthält nicht den Wert, sondern den Pfad zu einer Datei, in der der Wert steht.

    Leg die Datei an:

    echo 'geheim' > passwort.txt

    Erzeuge die Datenbank noch einmal neu – mit diesen beiden Angaben statt -e POSTGRES_PASSWORD=geheim:

    -v "$(pwd)/passwort.txt":/run/secrets/db-passwort
-e POSTGRES_PASSWORD_FILE=/run/secrets/db-passwort

    Hinweis: Nimm dafür ein frisches Volume, sonst ist die Datenbank schon eingerichtet und behält ihr altes Passwort. Dass es geklappt hat, siehst Du daran, dass der Container läuft: Ohne Passwort – egal auf welchem Weg – bricht er ab, wie beim ersten Versuch.

    Auf einer Betriebsplattform legt genau diese Datei nicht der Mensch an, sondern die Plattform – aus ihrer eigenen Verwaltung für Geheimnisse.

    Reflexionsfragen

    • Woher weißt Du, welche Umgebungsvariablen ein fremdes Image auswertet? Was passiert, wenn Du einen Namen falsch schreibst?
    • Mit dem Volume haben Deine Daten das Löschen des Containers überlebt. Wo liegen sie jetzt eigentlich, und wem gehören sie? Was wäre ohne Volume passiert?
    • Wo landen die Log-Ausgaben der Datenbank, und warum ist das für eine Betriebsplattform praktischer als eine Logdatei im Container?
    • Aus welchen Gründen ist POSTGRES_PASSWORD_FILE besser als POSTGRES_PASSWORD?
