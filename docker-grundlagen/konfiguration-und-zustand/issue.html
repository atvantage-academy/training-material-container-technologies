Eine Datenbank über Umgebungsvariablen konfigurieren

Als Entwickler möchte ich eine Datenbank einrichten, ohne ihr Image anzufassen, damit dasselbe Artefakt in Entwicklung, Test und Produktion unterschiedlich arbeiten kann.

Lernziele

Du…

  • setzt beim Erzeugen eines Containers Umgebungsvariablen und benennst, woher Du weißt, welche ein Image auswertet.
  • richtest eine PostgreSQL-Datenbank vollständig von außen ein – ohne Dockerfile, ohne Konfigurationsdatei.
  • rufst die Log-Ausgabe eines Containers ab und liest daraus, warum ein Start fehlgeschlagen ist.
  • betreibst zwei Container aus demselben Image mit verschiedenen Datenbanken und begründest, warum das ohne Neubau möglich ist.

Definition of Done

  • Ein Container meine-db läuft mit einer Datenbank namens helloworld.
  • Du hast per psql aus dem Container heraus geprüft, dass die Datenbank existiert und Deine Tabelle Daten enthält.
  • Du hast einen Startfehler absichtlich erzeugt und in der Log-Ausgabe gefunden, woran er lag.
  • Ein zweiter Container meine-db-test läuft aus demselben Image mit einer anderen Datenbank und einem anderen Port.
  • Du hast den ersten Container gestoppt, neu gestartet und geprüft, ob Deine Daten noch da sind.
  • Du hast die Reflexionsfragen schriftlich beantwortet.

Arbeitsschritte

Einen Start absichtlich scheitern lassen

Fang mit dem Fehler an – er erklärt Dir gleich, wie Du künftig Fehler findest.

docker container create --name db-versuch postgres:18

docker container start db-versuch

Der Container läuft nicht. Sieh nach, warum:

docker container logs db-versuch

Hinweis: Die Meldung sagt Dir genau, welche Angabe fehlt. docker logs ist ab jetzt Dein erster Griff, wenn etwas nicht tut.

Räum den gescheiterten Versuch weg:

docker container rm db-versuch

Die Datenbank über Umgebungsvariablen einrichten

Jede Angabe kommt mit einem eigenen -e von außen dazu.

docker container create --name meine-db -p 5432:5432 -e POSTGRES_DB=helloworld -e POSTGRES_USER=kurs -e POSTGRES_PASSWORD=geheim postgres:18

docker container start meine-db

Prüfe in der Log-Ausgabe, dass die Datenbank bereit ist:

docker container logs meine-db

Hinweis: Woher kommen die Namen POSTGRES_DB, POSTGRES_USER und POSTGRES_PASSWORD? Sieh im Datenblatt des Images auf Docker Hub nach. Merk Dir, wo diese Information steht – bei jedem anderen Image wirst Du sie dort wieder suchen.

Eine Tabelle anlegen und füllen

Du führst psql im Container aus – genau wie den echo-Befehl in der vorigen Übung.

docker container exec meine-db psql -U kurs -d helloworld -c "CREATE TABLE gruss (id SERIAL PRIMARY KEY, text TEXT NOT NULL)"

docker container exec meine-db psql -U kurs -d helloworld -c "INSERT INTO gruss (text) VALUES ('Hallo Welt'), ('Hello World'), ('Bonjour le monde')"

Sieh nach, ob die Daten da sind:

docker container exec meine-db psql -U kurs -d helloworld -c "SELECT * FROM gruss"

Einen Tippfehler bauen und beobachten

Lege einen weiteren Container an – diesmal mit einem falsch geschriebenen Variablennamen.

docker container create --name db-tippfehler -p 5433:5432 -e POSTGRES_DATABASE=helloworld -e POSTGRES_USER=kurs -e POSTGRES_PASSWORD=geheim postgres:18

docker container start db-tippfehler

docker container exec db-tippfehler psql -U kurs -d helloworld -c "SELECT 1"

Hinweis: Der Container startet – aber Dein Befehl scheitert. Überleg Dir, welche Datenbank stattdessen entstanden ist und warum niemand Dich gewarnt hat.

docker container stop db-tippfehler

docker container rm db-tippfehler

Dasselbe Image, eine andere Datenbank

Das ist der Kern der Übung. Kein Neubau, kein zweites Image – nur andere Werte.

docker container create --name meine-db-test -p 5433:5432 -e POSTGRES_DB=testdaten -e POSTGRES_USER=tester -e POSTGRES_PASSWORD=auchgeheim postgres:18

docker container start meine-db-test

docker container exec meine-db-test psql -U tester -d testdaten -c "\l"

docker images

Hinweis: Sieh Dir die Image-Liste an. Wie viele PostgreSQL-Images liegen bei Dir? Und wie viele verschieden konfigurierte Datenbanken betreibst Du gerade?

Stoppen, neu starten und nachsehen

docker container stop meine-db

docker container start meine-db

docker container exec meine-db psql -U kurs -d helloworld -c "SELECT * FROM gruss"

Hinweis: Notiere das Ergebnis. Was wäre nach einem docker container rm passiert? Probier es nicht aus – wir brauchen die Datenbank morgen noch.

Reflexionsfragen

  • Woher weißt Du, welche Umgebungsvariablen ein fremdes Image auswertet? Was passiert, wenn Du einen Namen falsch schreibst?
  • Was wäre nötig gewesen, um die Datenbank stattdessen über eine Konfigurationsdatei im Image einzurichten? Wie viele Images hättest Du für Entwicklung, Test und Produktion?
  • Deine Daten haben stop und start überlebt. Was erwartest Du nach einem docker container rm, und woran liegt das?
  • Wo landen die Log-Ausgaben der Datenbank, und warum ist das für eine Betriebsplattform praktischer als eine Logdatei im Container?
  • Was spricht dagegen, ein echtes Datenbank-Passwort so zu setzen, wie Du es hier getan hast?
