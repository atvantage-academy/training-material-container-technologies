    Wissens-Check: Docker-Grundlagen

    Siebzehn Fragen als Rückblick auf zwei Tage. Sie prüfen, was Du wiedererkennst – das ist weniger, als Du kannst, und mehr, als Du glaubst. Es gibt keine Note und keine Auswertung im Kurs; die Antworten siehst nur Du.

    Lies bei jeder Antwort auch die Begründung, wenn Du danebengegriffen hast. Sie ist der eigentliche Inhalt dieser Seite.

    1. Zwei Begriffe, die im Alltag oft durcheinandergehen.

      Was unterscheidet ein Docker-Image von einem Docker-Container?

      • Das Image ist der Bauplan, der Container eine laufende Ausprägung davon.

      • Das Image läuft im Vordergrund, der Container läuft im Hintergrund weiter.

      • Das Image liegt in der Registry, der Container liegt lokal auf der Platte.

      • Das Image enthält nur die Anwendung, der Container zusätzlich das Betriebssystem.

    2. Dieselbe Anwendung soll in Entwicklung, Test und Produktion unterschiedlich arbeiten.

      Wie sollte eine 12-Factor-App laut Faktor III („Config“) ihre Konfiguration bekommen?

      • Aus Umgebungsvariablen, die beim Start von außen gesetzt werden.

      • Aus einer Konfigurationsdatei, die beim Bauen fest ins Image kopiert wird.

      • Aus Kommandozeilenparametern, die beim Start des Containers übergeben werden.

      • Aus einer zentralen Datenbank, die jeder Dienst bei jeder Anfrage abfragt.

    3. Du willst einen Container im Hintergrund starten und ihm einen festen Namen geben.

      Welcher Aufruf ist dafür der richtige?

      • docker run -d –name meine-app nginx

      • docker run –name -d meine-app nginx

      • docker start -d –name meine-app nginx

      • docker create -d –name meine-app nginx

    4. Im Dockerfile stehen Anweisungen, die zu unterschiedlichen Zeitpunkten wirken.

      Welche Anweisung bestimmt, was beim Starten eines Containers ausgeführt wird?

      • CMD beziehungsweise ENTRYPOINT – beide wirken zur Startzeit.

      • RUN – die Anweisung führt den angegebenen Befehl im Container aus.

      • ENV – die Anweisung setzt die Umgebung, in der der Start abläuft.

      • EXPOSE – die Anweisung startet den Dienst auf dem genannten Port.

    5. Du baust ein Image mit docker image build . und vergisst den Parameter -t.

      Welchen Namen trägt das Image danach – und warum ist das unpraktisch?

      • Gar keinen – es erscheint als <none> und ist nur per ID ansprechbar.

      • Den Namen des Verzeichnisses, in dem das Dockerfile gerade liegt.

      • Den Namen des Basis-Images aus der FROM-Zeile mit dem Tag latest.

      • Einen zufällig erzeugten Namen, so wie Container ihn beim Start bekommen.

    6. Ein vollständiger Imagename lautet registry.example.com/team/app:1.4.2.

      Was bezeichnet dabei der Teil team/app?

      • Das Repository – den Platz für ein Image in vielen Ständen.

      • Die Registry – den Dienst, der die Images speichert und ausliefert.

      • Den Tag – die Kennzeichnung eines bestimmten Standes des Images.

      • Den Layer – die Schicht, aus der das Image beim Bauen entstanden ist.

    7. In einem Container läuft eine Datenbank. Der Container wird gelöscht und neu angelegt.

      Was passiert mit den Daten – und wie verhinderst Du den Verlust?

      • Sie sind weg. Ein Volume an der Datenablage hätte sie überleben lassen.

      • Sie bleiben im Image erhalten, sofern Du es vorher neu gebaut hast.

      • Sie bleiben erhalten, weil Docker den Schreibbereich automatisch sichert.

      • Sie sind weg. Nur ein erneutes docker commit hätte sie retten können.

    8. Zwei Container stehen zusammen in einem selbst angelegten Netzwerk.

      Wie erreicht der eine Container den anderen?

      • Über seinen Container-Namen, den Docker im Netzwerk auflöst.

      • Über localhost und den Port, den der andere Container belegt hat.

      • Über die IP-Adresse des Hosts und den veröffentlichten Port.

      • Über gar nichts: Container sind grundsätzlich voneinander abgeschottet.

    9. Eine Umgebung besteht aus Datenbank, Webserver und Anwendung mit Volumes und Netzwerk.

      Womit startest Du alle drei mit einem einzigen Befehl?

      • Mit Docker Compose und einer Datei, die alle Services beschreibt.

      • Mit docker run, dem Du alle drei Images hintereinander übergibst.

      • Mit einem Dockerfile, das die drei Images als Stufen zusammenfasst.

      • Mit docker network create, das alle Container darin gemeinsam startet.

    10. In einer Compose-Datei steht bei der Anwendung depends_on: [datenbank].

      Was garantiert diese Angabe – und was nicht?

      • Die Startreihenfolge, aber nicht, dass die Datenbank schon bereit ist.

      • Dass die Datenbank läuft und Verbindungen annimmt, bevor die App startet.

      • Dass die Anwendung neu startet, sobald die Datenbank neu gestartet wurde.

      • Dass beide Container im selben Netzwerk stehen und einander erreichen.

    11. Ein Prozess im Container läuft, antwortet aber auf keine Anfrage mehr.

      Wozu dient in dieser Lage ein HEALTHCHECK im Dockerfile?

      • Das Image sagt selbst, wie man prüft, ob es tatsächlich arbeitet.

      • Er startet den Container automatisch neu, sobald der Prozess endet.

      • Er prüft beim Bauen, ob alle Abhängigkeiten im Image vorhanden sind.

      • Er meldet an die Registry zurück, ob das Image fehlerfrei gezogen wurde.

    12. Du führst docker container stop meine-app aus und suchst den Container anschließend.

      Warum erscheint er in docker container ls nicht mehr?

      • Weil der Befehl nur laufende Container zeigt – mit -a siehst Du ihn wieder.

      • Weil stop den Container samt seines Schreibbereichs endgültig entfernt.

      • Weil angehaltene Container automatisch in die Registry zurückgeschrieben werden.

      • Weil der Name nach dem Anhalten freigegeben und der Eintrag gelöscht wird.

    13. Ein Team überlegt, Anwendung und Datenbank gemeinsam in einem Container zu betreiben.

      Was spricht am deutlichsten dagegen?

      • Beide hätten denselben Lebenszyklus und ließen sich nicht getrennt ersetzen.

      • Ein Container kann technisch immer nur einen einzigen Prozess ausführen.

      • Datenbanken lassen sich in Containern grundsätzlich nicht sinnvoll betreiben.

      • Das gemeinsame Image würde die zulässige Maximalgröße einer Registry sprengen.

    14. Auf einer Plattform werden Container laufend beendet, verschoben und neu gestartet.

      Welche Eigenschaft muss eine Anwendung dafür mitbringen?

      • Zustandslosigkeit – zwischen zwei Anfragen bleibt nichts im Speicher.

      • Ein möglichst kleines Image, damit das Verschieben schnell genug abläuft.

      • Einen Healthcheck, damit die Plattform den Zustand jederzeit abfragen kann.

      • Eine eigene Sitzungsverwaltung, die jeden Container gezielt wiederfindet.

    15. In Produktion läuft anwendung:latest. Heute Nacht ist etwas kaputtgegangen.

      Welches Vorgehen hätte die Fehlersuche überhaupt erst möglich gemacht?

      • Feste Versions-Tags veröffentlichen und im Betrieb darauf verweisen.

      • Das Tag latest nach jedem Push zusätzlich mit einem Datum versehen.

      • Die Registry so einstellen, dass sie jeden Push automatisch aufbewahrt.

      • Auf das Pinnen verzichten, damit immer die neuesten Korrekturen ankommen.

    16. Dein Dockerfile kopiert erst den gesamten Code, dann installiert es die Abhängigkeiten. Du änderst eine Zeile Code und baust neu.

      Warum dauert der Bau so lange wie beim ersten Mal?

      • Weil der geänderte Layer alle folgenden Layer ungültig macht.

      • Weil der Build-Cache nach jeder Änderung am Arbeitsverzeichnis verworfen wird.

      • Weil pip bei jedem Lauf prüft, ob es neuere Fassungen der Pakete gibt.

      • Weil ein Layer mit kopierten Dateien grundsätzlich nicht zwischengespeichert wird.

    17. Ein Dockerfile installiert in einer Zeile ein Paket und löscht in der nächsten die Paketlisten.

      Warum ist das Image trotzdem nicht kleiner?

      • Weil der frühere Layer bleibt und der spätere die Dateien nur überdeckt.

      • Weil das Löschen erst beim Start des Containers wirksam wird.

      • Weil die Paketlisten im Basis-Image liegen und dort nicht erreichbar sind.

      • Weil Docker gelöschte Dateien zur Sicherheit aufbewahrt, bis das Image gepusht wird.

    Wie es weitergeht

    • Ab 85 % richtig – Sitzt. Die Grundlagen tragen. Nimm Dir für den nächsten Schritt die Best Practices vor – und bau Dein erstes eigenes Projekt-Image um.
    • Ab 60 % richtig – Gutes Fundament. Das Meiste sitzt. Geh die Stellen, bei denen Du geschwankt hast, noch einmal an: Der Lebenszyklus und die zwölf Faktoren klären die meisten Rückfragen.
    • Unter 60 % – Noch Luft. Fang bei zwei Seiten an: dem Lebenszyklus eines Containers und den zwölf Faktoren. Fast alles Weitere hängt an diesen beiden.
