Layer und Build-Cache

Ein Image entsteht nicht in einem Stück. Es entsteht Schicht für Schicht – und wer diese Schichtung versteht, versteht anschließend von selbst, warum ein zweiter Build Sekunden statt Minuten braucht.

Ein Dockerfile, Schicht für Schicht

Ein Dockerfile ist eine Liste von Schritten. Jeder Schritt geht von dem Ergebnis des vorherigen aus:

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
CMD ["node", "server.js"]

Alle Anweisungen und ihre Feinheiten stehen in der offiziellen Dockerfile-Referenz. Für diese Seite genügen die sechs oben.

Jede dieser Zeilen legt eine Schicht an. Das Bild folgt der Datei – Zeile 1 zuerst, Zeile 6 zuletzt:

  • 1node:20-alpineGrund
  • 2WORKDIR /appnur Metadaten
  • 3package*.jsonSchicht
  • 4node_modulesSchicht
  • 5AnwendungsdateienSchicht
  • 6CMD …nur Metadaten

untere Schichten

obere Schichten

Die Pfeile geben die Sprache vor. Eine Schicht baut immer auf dem auf, was vor ihr entstanden ist: FROM ist die unterste Schicht, die letzte Zeile die oberste. Wenn auf dieser Seite von unteren und oberen Schichten die Rede ist, ist das gemeint – die frühere und die spätere Zeile.

Nicht jede Zeile wird zu einer Schicht. Nur RUN, COPY und ADD verändern das Dateisystem und legen damit eine an. FROM setzt den Grund, und WORKDIR, ENV, EXPOSE, CMD oder ENTRYPOINT schreiben nur Angaben ins Image – sie kosten keinen Platz, gehören aber trotzdem dazu.

Jeder Layer trägt einen Hash

Beim Bauen bekommt jede Schicht eine Prüfsumme – einen Hash. Er entsteht aus zwei Dingen: aus dem Inhalt der Schicht selbst und aus dem Hash der Schicht, auf der sie liegt.

Hash(Layer) = f( Inhalt des Layers, Hash des Layers darunter )

Damit benennt ein Hash nie nur eine Schicht, sondern die ganze Kette unter ihr. Zwei Bauläufe, bei denen dieselben Schritte auf demselben Grund landen, ergeben denselben Hash:

  • node:20-alpinesha256:1f4c…
  • package*.jsonsha256:9a02…
  • node_modulessha256:c771…
  • Anwendungsdateiensha256:3e8b…

Jeder Hash steckt in den Hashes darunter mit drin.

Daraus folgt beides, was diese Seite ausmacht:

  • Der Cache. Kennt Docker einen Hash bereits, muss es die Schicht nicht erneut bauen und nicht erneut herunterladen. Es genügt der Verweis auf das, was schon da ist.
  • Die Ungültigkeit nach oben. Ändert sich eine Schicht, ändert sich ihr Hash – und damit zwangsläufig der Hash jeder darüberliegenden, auch wenn deren Anweisung Wort für Wort dieselbe geblieben ist. Sie steht ja auf einem anderen Grund.

Ein Image ist ein Layer und alles darunter

Damit lässt sich sagen, was ein Image eigentlich ist:

Ein Image ist nichts anderes als ein Layer samt allem, was unter ihm liegt. Der Name meine-app:1.0 zeigt auf das oberste Glied einer Kette – die Kette selbst ist das Image.

Das klingt nach Wortklauberei und hat zwei sehr praktische Folgen.

Zwei Images, ein gemeinsamer Grund

Zwei Images, die auf demselben Grund aufsetzen, teilen sich dessen Schichten – dieselben Hashes, dieselben Daten, einmal auf der Platte:

Gemeinsamer Grund – einmal vorhanden, von beiden benutzt:

  • node:20-alpinesha256:1f4c…
  • node_modules
  • Bestell-Anwendung

bestellung:2.1

  • node_modules
  • Versand-Anwendung

versand:1.4

Deshalb geht das Herunterladen des zweiten Images so viel schneller als das des ersten: Was schon liegt, wird nicht noch einmal geholt.

Ein Image als Grund für das nächste

Und weil ein Image nur eine Kette ist, kann ein Dockerfile auch auf einem eigenen Image aufsetzen statt auf einem fremden:

FROM meine-basis:1.0
COPY . .
CMD ["node", "server.js"]

meine-basis:1.0 – ein vollständiges Image, das hier nur der Grund ist:

  • node:20-alpinevon der Basis geerbt
  • Werkzeuge, Zertifikate, Benutzervon der Basis geerbt
  • Anwendungsdateien

meine-app:2.0

So arbeiten Häuser mit vielen Anwendungen: ein gepflegtes Basis-Image, darauf viele dünne Anwendungs-Images. Wird die Basis erneuert, erben es alle – und alle müssen neu gebaut werden, denn ihr Grund hat einen neuen Hash bekommen.

Was der Cache daraus macht

Jetzt lohnt sich der Blick auf die Reihenfolge der Zeilen. Unten stehen zweimal dieselben Anweisungen – links in der naheliegenden Reihenfolge, rechts in der, die den Cache trägt. Gezeigt ist der zweite Build, nachdem sich eine Quelldatei geändert hat.

Naheliegend – und teuer

Erst alles kopieren, dann installieren.

  • FROM node:20-alpineaus dem Cache
  • COPY . .neu gebaut
  • RUN npm installneu gebaut
  • CMD ["node", "server.js"]nur Metadaten

Eine Zeile Code geändert – und die Abhängigkeiten werden erneut heruntergeladen und installiert. Bei jedem Build. Jeden Tag.

Stabiles zuerst

Erst die Abhängigkeitsliste, dann installieren, dann der Rest.

  • FROM node:20-alpineaus dem Cache
  • COPY package*.json ./aus dem Cache
  • RUN npm installaus dem Cache
  • COPY . .neu gebaut
  • CMD ["node", "server.js"]nur Metadaten

Dieselbe Änderung – der teure Schritt bleibt liegen, weil sich die Abhängigkeitsliste nicht geändert hat. Erst wenn sie sich ändert, wird wieder installiert.

Der Nebenbefund, der überrascht

Ein Layer, in dem eine Datei gelöscht wird, macht das Image nicht kleiner. Die Datei steckt weiterhin im Layer darunter – der obere merkt sich nur, dass sie nicht mehr zu sehen ist.

Zwei Anweisungen – Ballast bleibt

  • FROM debian:12-slimBasis
  • RUN apt-get update && apt-get install -y curl+ Paketlisten
  • RUN rm -rf /var/lib/apt/lists/*nur unsichtbar

Eine Anweisung – Ballast weg

  • FROM debian:12-slimBasis
  • RUN apt-get update && apt-get install -y curl \
      && rm -rf /var/lib/apt/lists/*    sauber

Merksatz: Was sich selten ändert, gehört nach unten. Was aufgeräumt werden soll, muss im selben Layer aufgeräumt werden, in dem es entstanden ist.
