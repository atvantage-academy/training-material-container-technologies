Ein Image versioniert in eine Registry pushen

Als Entwickler möchte ich mein Image an einem Ort ablegen, an den andere herankommen, damit nicht jeder es selbst bauen muss – und damit später nachvollziehbar bleibt, welche Fassung wo lief.

Lernziele

Du…

  • meldest Dich an einer Registry an und legst dort ein Repository an.
  • versiehst ein lokales Image mit dem vollständigen Namen seines Ziels und erklärst, woraus dieser Name besteht.
  • veröffentlichst dasselbe Image unter einem Versions-Tag und unter einem beweglichen Zeiger.
  • begründest, warum ein Verlass auf latest ein Zurückrollen unmöglich macht.

Definition of Done

  • Du bist an der Registry angemeldet und hast dort ein Repository meine-website angelegt.
  • Dein Image liegt in der Registry unter dem Tag 1.0.0.
  • Dasselbe Image liegt dort zusätzlich unter dem Tag latest.
  • Eine zweite Fassung liegt als 1.0.1 in der Registry, und latest zeigt auf sie.
  • Du hast Dein Image lokal gelöscht und aus der Registry zurückgeholt.
  • Du hast die Reflexionsfragen schriftlich beantwortet.

Arbeitsschritte

Ein Repository anlegen und sich anmelden

Leg in der Registry ein Repository namens meine-website an – das geht über die Weboberfläche der Registry.

Melde Dich anschließend auf der Kommandozeile an:

docker login

Hinweis: Nutzt Dein Konto eine zweistufige Anmeldung, brauchst Du hier ein Zugriffstoken statt Deines Passworts. Das legst Du in den Einstellungen Deines Registry-Kontos an.

Dem Image den Namen seines Ziels geben

Ein Image muss so heißen wie der Ort, an den es soll. Ersetze <dein-konto> durch Deinen Kontonamen.

docker image tag meine-website:1.0.0 <dein-konto>/meine-website:1.0.0

docker images

Hinweis: Vergleiche die Spalte IMAGE ID der beiden Zeilen. Wie viele Images hast Du jetzt – und wie viele Namen?

Das Image veröffentlichen

docker image push <dein-konto>/meine-website:1.0.0

Hinweis: Sieh Dir an, was während des Pushs zeilenweise passiert. Jede Zeile ist ein Layer. Merk Dir, wie lange es gedauert hat.

Sieh in der Weboberfläche der Registry nach, ob Dein Image angekommen ist.

Einen beweglichen Zeiger daneben setzen

docker image tag meine-website:1.0.0 <dein-konto>/meine-website:latest

docker image push <dein-konto>/meine-website:latest

Hinweis: Dieser Push war deutlich schneller als der erste. Überleg Dir, warum – die Antwort hat mit den Layern von gestern zu tun.

Eine zweite Fassung veröffentlichen

Ändere Deine Seite und bau eine neue Version:

echo "<h1>Meine Seite, dritte Fassung</h1>" > index.html

docker image build -t <dein-konto>/meine-website:1.0.1 .

docker image push <dein-konto>/meine-website:1.0.1

Zieh jetzt den beweglichen Zeiger nach:

docker image tag <dein-konto>/meine-website:1.0.1 <dein-konto>/meine-website:latest

docker image push <dein-konto>/meine-website:latest

Hinweis: Sieh Dir in der Registry an, welche Tags jetzt auf welchem Stand liegen. Und dann die Frage, auf die es ankommt: Wenn jemand gestern <dein-konto>/meine-website:latest gezogen hat – welche Fassung hat er bekommen? Und wie fändest Du das heute noch heraus?

Das Image zurückholen

Lösch Deine lokalen Kopien und hol Dir die veröffentlichte Fassung:

docker image rm <dein-konto>/meine-website:1.0.0

docker image rm <dein-konto>/meine-website:latest

docker image pull <dein-konto>/meine-website:1.0.0

docker images

Reflexionsfragen

  • Wie weist Du einem bereits gepushten Image zusätzlich das Tag latest zu? Musst Du es dafür neu bauen?
  • Welche Schritte führst Du aus, um eine Änderung als Version 1.0.1 zu veröffentlichen und latest mitzuziehen? In welcher Reihenfolge – und warum nicht umgekehrt?
  • Was passiert, wenn Du ein Image nur mit dem Tag latest pushst und dieses Tag bei jeder Änderung verschiebst? Was kannst Du dann nicht mehr?
  • Warum war der zweite Push so viel schneller als der erste?
  • Was passiert, wenn Du im Dockerfile bei FROM das Tag weglässt? Warum ist das für einen Build, den jemand in einem halben Jahr wiederholt, ein Problem?
