Ein Dockerfile gegen die Praxis prüfen

Als Mitglied des Teams möchte ich ein Dockerfile lesen und benennen können, was daran im Betrieb Ärger machen wird, damit wir das im Review finden und nicht in der Störung.

Lernziele

Du…

  • benennst an einem gegebenen Dockerfile mindestens vier Stellen, die im Betrieb Probleme machen, und begründest jede.
  • baust ein Dockerfile auf einen Multi-Stage-Build um und erklärst, was dadurch aus dem Ergebnis verschwindet.
  • lässt den Prozess im Container unter einem eigenen Benutzer laufen.
  • misst den Unterschied zwischen zwei Images und ordnest ein, woher er kommt.

Definition of Done

  • Du hast allein eine Liste mit Befunden zum vorgegebenen Dockerfile erstellt und sie anschließend mit Deiner Partnerin verglichen.
  • Das Ausgangs-Image ist gebaut, und Du kennst seine Größe.
  • Eine überarbeitete Fassung ist gebaut, nutzt einen Multi-Stage-Build, gepinnte Versionen und einen eigenen Benutzer.
  • Du kennst beide Größen und kannst sagen, woher der größte Anteil der Ersparnis kommt.
  • Der Container aus der überarbeiteten Fassung läuft und antwortet.
  • Du hast die Reflexionsfragen schriftlich beantwortet.

Arbeitsschritte

Das Ausgangsmaterial anlegen

mkdir ~/review

cd ~/review

echo "<h1>Review</h1>" > index.html

nano Dockerfile

Schreib genau dieses Dockerfile hinein – es ist absichtlich schlecht:

FROM debian:latest
RUN apt-get update
RUN apt-get install -y nginx curl git build-essential
RUN rm -rf /var/lib/apt/lists/*
COPY . /usr/share/nginx/html/
EXPOSE 80
CMD nginx -g "daemon off;"

Allein prüfen – noch nicht reden

Nimm Dir fünf Minuten für Dich und notiere alles, was Dir auffällt. Eine Zeile je Befund: welche Zeile, was ist das Problem, was wäre die Folge im Betrieb.

Hinweis: Sprich jetzt noch nicht mit Deiner Partnerin. Die Übung lebt davon, dass zwei Listen entstehen. Als Nachschlagewerk hilft Dir Best Practices für Container Images.

Die Listen vergleichen

Geht beide Listen durch. Markiert die Punkte, die nur eine von Euch gefunden hat – über die lohnt es sich zu reden.

Das schlechte Image bauen und messen

docker image build -t review:schlecht .

docker images review

Hinweis: Schreib die Größe auf. Sie ist Dein Vergleichswert.

Die überarbeitete Fassung schreiben

nano Dockerfile.gut

Bau die Datei selbst um. Dieses Gerüst zeigt Dir die Multi-Stage-Schreibweise – den Rest entscheidest Du anhand Deiner Befundliste:

FROM debian:12-slim AS aufbereitung
WORKDIR /arbeit
COPY index.html .
RUN echo "<p>gebaut in der Aufbereitungsstufe</p>" >> index.html

FROM nginx:1.27.5-alpine
COPY --from=aufbereitung /arbeit/index.html /usr/share/nginx/html/index.html
USER nginx
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

Hinweis: Achte auf drei Unterschiede zur Ausgangsfassung, die leicht zu übersehen sind: die Form von CMD (eckige Klammern statt einer Zeichenkette), die Herkunft der kopierten Datei (--from=) und den Benutzer.

Die überarbeitete Fassung bauen und vergleichen

docker image build -f Dockerfile.gut -t review:gut .

docker images review

Hinweis: Wie groß ist der Unterschied? Überleg Dir, welcher einzelne Eingriff den größten Anteil daran hat.

Prüfen, dass sie auch läuft

docker run -d --name review-gut -p 8090:80 review:gut

curl http://localhost:8090

docker container exec review-gut whoami

Hinweis: Führ denselben whoami-Befehl gedanklich für das schlechte Image aus. Welchen Benutzer bekämst Du dort?

Einen Scan laufen lassen

Nur, wenn ein Scanner zur Verfügung steht – frag Deinen Trainer.

docker scout cves review:schlecht

docker scout cves review:gut

Hinweis: Vergleiche die Anzahl der Befunde. Und dann die wichtigere Frage: Was von dem, was ein Scanner findet, betrifft Deine Anwendung überhaupt?

Aufräumen

docker container stop review-gut

docker container rm review-gut

Reflexionsfragen

  • Welchen Befund hat nur eine von Euch beiden gefunden? Woran lag das?
  • Wie viel kleiner ist das überarbeitete Image, und woher kommt der größte Anteil der Ersparnis?
  • Im schlechten Dockerfile werden die Paketlisten in einer eigenen Zeile gelöscht. Warum wird das Image dadurch nicht kleiner?
  • Was ändert USER praktisch, und warum verlangen manche Plattformen es?
  • Warum sollte ein Image regelmäßig neu gebaut werden, auch wenn sich an Deinem Code nichts geändert hat?
  • Was findet ein Sicherheits-Scan nicht? Was folgt daraus für den Umgang mit seinem Ergebnis?
