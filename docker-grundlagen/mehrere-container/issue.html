Die ganze Landschaft mit einem Befehl starten

Als Mitglied des Teams möchte ich unsere Umgebung in einer Datei beschreiben, damit eine neue Kollegin sie mit einem Befehl aufbauen kann – ohne dass ihr jemand fünfzehn docker-Aufrufe diktiert.

Lernziele

Du…

  • überführst eine Folge von docker-Befehlen in eine Compose-Beschreibung und ordnest jeden Parameter dem passenden Schlüssel zu.
  • startest, stoppst und entfernst eine mehrteilige Umgebung mit je einem Befehl.
  • sprichst einen Service von einem anderen aus über seinen Servicenamen an, ohne ein Netzwerk angelegt zu haben.
  • unterscheidest down von down -v und benennst, was jeweils verloren geht.
  • erklärst, was depends_on garantiert und was nicht.

Definition of Done

  • Eine Datei compose.yaml beschreibt zwei Services: datenbank und webapp.
  • docker compose up -d startet beide, docker compose ps zeigt sie.
  • Deine Anwendung antwortet unter Port 8080 mit den Daten aus der Datenbank.
  • Die Anwendung erreicht die Datenbank über den Namen datenbank – ohne dass Du ein Netzwerk angelegt hast.
  • Nach docker compose down und erneutem up -d sind Deine Tabellendaten noch da.
  • Du hast die Reflexionsfragen schriftlich beantwortet.

Arbeitsschritte

Aufräumen und ein Projektverzeichnis anlegen

Die Container aus den vorigen Übungen belegen Namen und Ports.

docker container rm -f meine-db

mkdir ~/meine-landschaft

cd ~/meine-landschaft

Die Vorlage übernehmen und anpassen

Du bekommst die Beschreibung als Vorlage. Deine Aufgabe ist nicht, sie zu tippen, sondern sie zu verstehen und an Deine Landschaft anzupassen.

Leg compose.yaml mit diesem Inhalt an:

services:

  datenbank:
    image: postgres:16
    environment:
      POSTGRES_USER: kurs
      POSTGRES_PASSWORD: geheim
      POSTGRES_DB: helloworld
    volumes:
      - kurs-daten:/var/lib/postgresql/data

  webapp:
    image: MEIN-IMAGE:MEINE-VERSION
    environment:
      DATABASE_URL: postgresql://kurs:geheim@datenbank:5432/helloworld
    ports:
      - "8080:8080"
    depends_on:
      - datenbank

volumes:
  kurs-daten:

Pass drei Dinge an:

  1. Das Image Deiner Webanwendung – der Name, den Du beim Bauen vergeben hast.
  2. Den Hostnamen in DATABASE_URL – vergleiche ihn mit dem Namen, unter dem die Datenbank in den vorigen Übungen lief. Was fällt Dir auf?
  3. Den Port, falls 8080 bei Dir belegt ist.

Hinweis: Ein Netzwerk steht nicht in der Datei. Compose legt für jedes Projekt eines an und hängt alle Services hinein – sie erreichen einander über ihren Servicenamen. Genau deshalb steht dort datenbank und nicht meine-db.

Hinweis: Das Volume steht zweimal in der Datei: einmal beim Service, der es benutzt, und einmal unten in der Liste der Volumes. Das untere ist die Anmeldung, das obere die Verwendung.

Die Landschaft starten

docker compose up -d

docker compose ps

Nachsehen, was Compose angelegt hat

docker network ls

docker volume ls

Hinweis: Du hast weder ein Netzwerk noch ein Volume von Hand angelegt. Trotzdem sind beide da. Merk Dir die Namen – woraus sind sie gebildet?

Die Tabelle anlegen und Daten hineinschreiben

Das Volume ist neu, die Tabelle gibt es also noch nicht.

docker compose exec datenbank psql -U kurs -d helloworld -c "CREATE TABLE gruss (id SERIAL PRIMARY KEY, text TEXT NOT NULL)"

docker compose exec datenbank psql -U kurs -d helloworld -c "INSERT INTO gruss (text) VALUES ('Hallo aus Compose')"

curl http://localhost:8080

Hinweis: Beachte, was hier nicht steht: kein docker network create, keine IP-Adresse, kein veröffentlichter Port an der Datenbank. Woher kennt die Anwendung die Adresse der Datenbank?

Alles wegräumen und wieder aufbauen

docker compose down

docker compose ps -a

docker compose up -d

curl http://localhost:8080

Hinweis: Die Container waren weg und sind neu. Die Daten sind da. Erklär Dir selbst, warum – Du hast die Antwort in der Übung zu Konfiguration und Zustand erarbeitet.

In die Log-Ausgaben sehen

docker compose logs datenbank

Hinweis: Such in der Ausgabe die Zeile, ab der die Datenbank Verbindungen annimmt. Wie lange hat es vom Start bis dahin gedauert? Was hieße das für einen Service, der sich sofort verbinden will?

Bonus (freiwillig): wirklich warten statt nur starten

Nur, wenn Du früh fertig bist. depends_on wartet bloß auf den Start der Datenbank, nicht auf ihre Bereitschaft. Bring Compose dazu, wirklich zu warten.

Ergänze beim Service datenbank eine Prüfung:

    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U kurs -d helloworld"]
      interval: 5s
      retries: 10

Und schreib beim Service webapp die Abhängigkeit in der ausführlichen Form:

    depends_on:
      datenbank:
        condition: service_healthy

Dann von vorn, mit leerem Volume:

docker compose down -v

docker compose up -d

docker compose ps

Achtung: down -v löscht das Volume – und damit Deine Tabelle. Genau deshalb steht dieser Befehl erst hier und nicht weiter oben.

Reflexionsfragen

  • Welches Netzwerk hast Du angelegt, damit die Services einander finden?
  • Wodurch unterscheidet sich der Servicename vom Container-Namen? Welcher von beiden ist die Adresse?
  • Was garantiert depends_on – und was garantiert es ausdrücklich nicht? Welchen Fehler erzeugt diese Verwechslung, und wann fällt er auf?
  • Was ist der Unterschied zwischen docker compose down und docker compose down -v?
  • Was hat sich gegenüber den Einzelbefehlen der vorigen Übungen inhaltlich geändert – und was nicht?
  • Würdest Du eine solche Datei für den Produktionsbetrieb verwenden? Woran würdest Du merken, dass sie nicht mehr reicht?
