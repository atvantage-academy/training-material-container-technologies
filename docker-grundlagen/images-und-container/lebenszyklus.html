Der Lebenszyklus eines Containers

Ein Container ist kein Ding, sondern ein Zustand. Links steht, in welchem Zustand er gerade ist, dazwischen der Befehl, der ihn in den nächsten bringt – und rechts, was das für Deine Daten bedeutet.

Die beiden Übergänge, auf die es ankommt, sind stop und rm. Sie sehen ähnlich aus und tun etwas völlig Verschiedenes.

In der Registry nginx:1.27.5

Das Image liegt irgendwo im Netz. Auf Deinem Rechner ist noch nichts.

docker pull
Lokal vorhanden docker images

Das Image liegt auf der Platte – unveränderlich. Aus ihm können beliebig viele Container entstehen.

docker container create
Erzeugt created

Der Container existiert, aber es läuft nichts. docker container ls zeigt ihn nicht – ls -a schon.

docker container start
Läuft running

Hier passiert alles: Der Prozess im Container arbeitet, schreibt Dateien, nimmt Anfragen an.

docker container stop
Angehalten exited

Alles bleibt erhalten. Ein start bringt den Container samt seiner Änderungen zurück – der Weg nach oben ist offen.

docker container rm
Gelöscht —

Alles ist weg. Das Image liegt noch da; ein neuer Container daraus startet wieder im Auslieferungszustand.

Und docker run? Das ist kein eigener Zustand, sondern eine Abkürzung:

  • docker run = create + start in einem Befehl.
  • docker run --rm = create + start + rm, sobald der Prozess endet.

Bequem – aber wer damit anfängt, sieht die beiden Schritte nie getrennt. Genau deshalb kommt die Abkürzung hier zuletzt.

Merksatz: stop hält an, rm wirft weg. Was ein Container behalten soll, darf deshalb nicht in ihm liegen.
