Layer und Build-Cache

Ein Image entsteht nicht in einem Stück, sondern Schicht für Schicht. Wer das versteht, versteht den Rest von selbst.

Dockerfile – Liste von Schritten

Jeder Schritt geht vom Ergebnis des vorherigen aus:

Dockerfile

  1. FROM node:20-alpine
  2. WORKDIR /app
  3. COPY package*.json ./
  4. RUN npm install
  5. COPY . .
  6. CMD ["node", "server.js"]

Alle Anweisungen und ihre Feinheiten stehen in der offiziellen Dockerfile-Referenz. Für diese Seite genügen die sechs oben.

Jede Zeile legt eine Schicht an

Links die Datei, rechts was daraus entsteht – Zeile für Zeile:

  1. 1FROM node:20-alpine (Basis: mehrere Schichten)
  2. 2WORKDIR /app Metadaten
  3. 3COPY package*.json ./ Dateisystem
  4. 4RUN npm install Dateisystem
  5. 5COPY . . Dateisystem
  6. 6CMD ["node", "server.js"] Metadaten

untere Schichten

obere Schichten

Eine Dateisystem-Schicht legen nur RUN, COPY und ADD an; alles andere schreibt Metadaten. WORKDIR ist dabei der Grenzfall: Es schreibt Metadaten, legt das Verzeichnis aber an, wenn es fehlt – und es bestimmt, worauf sich die folgenden COPY- und RUN-Zeilen beziehen.

Die Pfeile geben die Sprache vor: FROM ist die unterste Schicht, die letzte Zeile die oberste – gemeint ist die frühere und die spätere Zeile.

Jeder Layer trägt einen Hash

Beim Bauen bekommt jede Schicht eine Prüfsumme – einen Hash. Er entsteht aus zwei Dingen: aus dem Inhalt der Schicht selbst und aus dem Hash der Schicht, auf der sie liegt.

Hash(Schicht) = ƒ( Inhalt der Schicht, Hash der Schicht darunter )

Zwei Bauläufe, bei denen dieselben Schritte auf demselben Grund landen, ergeben denselben Hash:

  • 1FROM node:20-alpinesha256:1f4c…
  • 2WORKDIR /appsha256:5b8d…
  • 3COPY package*.json ./sha256:9a02…
  • 4RUN npm installsha256:c771…
  • 5COPY . .sha256:3e8b…
  • 6CMD ["node", "server.js"]sha256:7d14…

Jeder Hash steckt in den Hashes darunter mit drin.

Geänderter Hash – alles Spätere neu

Ändert sich eine Schicht, ändert sich ihr Hash – und damit der Hash jeder darüberliegenden, auch wenn deren Anweisung Wort für Wort dieselbe ist. Sie steht ja auf einem anderen Grund.

  • 1FROM node:20-alpinesha256:1f4c…unverändert
  • 2WORKDIR /appsha256:5b8d…unverändert
  • 3COPY package*.json ./sha256:9a02…unverändert
  • 4RUN npm installsha256:c771…unverändert
  • 5COPY . .sha256:b0f2…neuer Hash
  • 6CMD ["node", "server.js"]sha256:44a9…neuer Hash

Eine Zeile geändert – ab dort bekommt jede Schicht einen neuen Hash.

Caching: Bekannter Hash, nichts zu tun

Vor dem Holen vergleicht Docker Hashes, keine Namen. Was schon auf der Platte liegt, wird nicht noch einmal geladen:

  1. meine-app:2.0 soll herCache
  2. 1FROM node:20-alpinesha256:1f4c…sha256:1f4c…
  3. 2WORKDIR /appsha256:5b8d…sha256:5b8d…
  4. 3COPY package*.json ./sha256:9a02…sha256:9a02…
  5. 4RUN npm installsha256:c771…sha256:c771…
  6. 5COPY . .sha256:b0f2…
  7. 6CMD ["node", "server.js"]sha256:44a9…

Vier Schichten liegen schon da. Die beiden fehlenden werden geholt – und landen danach ebenfalls im Cache.

Was ein Image wirklich ist

Ein Image ist kein Klotz, sondern ein Name auf einer Schicht – samt allem, was unter ihr liegt.

  1. 1FROM node:20-alpinenode:20-alpine
  2. 2WORKDIR /app
  3. 3COPY package*.json ./
  4. 4RUN npm install
  5. 5COPY . .
  6. 6CMD ["node", "server.js"]meine-app:2.0

Deshalb zeigen zwei Namen auf dieselbe Kette, nur an verschiedenen Stellen – und deshalb entsteht ein neues Image auch dann, wenn sich nur der Startbefehl ändert.

Zwei Images, ein gemeinsamer Grund

Zwei Images, die auf demselben Grund aufsetzen, teilen sich dessen Schichten – derselbe Hash, dieselben Daten, einmal auf der Platte. Darüber hat jedes seine eigenen Zeilen und damit eigene Hashes:

Gemeinsamer Grund – einmal vorhanden, von beiden benutzt:

  • FROM node:20-alpinesha256:1f4c…
  • COPY bestellung/ ./sha256:2c90…
  • RUN npm installsha256:6ea1…

bestellung:2.1

  • COPY versand/ ./sha256:d47b…
  • RUN npm installsha256:0f55…

versand:1.4

Deshalb geht das Herunterladen des zweiten Images so viel schneller als das des ersten: Was schon liegt, wird nicht noch einmal geholt.

Ein Image als Grund für das nächste

Und weil ein Image nur eine Kette ist, kann ein Dockerfile auch auf einem eigenen Image aufsetzen statt auf einem fremden:

Dockerfile

Schichten des Images

1FROM meine-basis:1.0 FROM node:20-alpinesha256:1f4c… RUN apk add …sha256:8b3f… meine-basis:1.0 2COPY . . COPY . .sha256:3e8b… 3CMD ["node", …] CMD […]sha256:44a9… meine-app:2.0

So arbeiten Häuser mit vielen Anwendungen:

Ein gepflegtes Basis-Image, darauf viele dünne Anwendungs-Images. Wird die Basis erneuert, erben es alle – und alle müssen neu gebaut werden!

Die Reihenfolge entscheidet!

Wähle das Szenario.

Entwickler ändert:

Naheliegend – und teuer

Erst alles kopieren, dann installieren.

  • FROM node:20-alpineaus dem Cache
  • COPY . .aus dem Cache
  • RUN npm installaus dem Cache

läuft optimal

Der ganze Stapel kommt aus dem Cache. Der Build dauert Sekunden.

installiert ohne Grund

Eine Zeile Code geändert – und die Abhängigkeiten werden erneut heruntergeladen und installiert. Bei jedem Build. Jeden Tag.

kein Unterschied

Hier wie dort dasselbe Bild: Diese Reihenfolge kann die beiden Fälle gar nicht unterscheiden.

Stabiles zuerst

Erst die Abhängigkeitsliste, dann installieren, dann der Rest.

  • FROM node:20-alpineaus dem Cache
  • COPY package*.json ./aus dem Cache
  • RUN npm installaus dem Cache
  • COPY . .aus dem Cache

läuft optimal

Alles aus dem Cache, wie nebenan.

nur die Dateien

Der teure Schritt bleibt liegen, weil die Abhängigkeitsliste unberührt ist.

zu Recht installiert

Die Liste hat sich geändert, also muss sie neu aufgelöst werden. Der Preis fällt nur an, wenn er anfällt.

Löschen macht ein Image nicht kleiner

Ein Layer, in dem eine Datei gelöscht wird, macht das Image nicht kleiner. Die Datei steckt weiterhin im Layer darunter – der obere merkt sich nur, dass sie nicht mehr zu sehen ist.

2 Layer

  • FROM debian:12-slimsha256:5d1a…
  • RUN apt-get install …sha256:9f3c…
  • RUN rm -rf …sha256:c0b8…

Ballast bleibt

Die Paketlisten stecken weiter im Layer darunter – der obere merkt sich nur, dass sie nicht mehr zu sehen sind.

1 Layer

  • FROM debian:12-slimsha256:5d1a…
  • RUN apt-get install … && rm -rf …sha256:7a44…

Ballast weg

Aufgeräumt wird im selben Layer, in dem der Ballast entstanden ist – dann taucht er gar nicht erst auf.

Zum Mitnehmen

  1. Ein Image ist ein Name auf einer Schicht – samt allem, was unter ihr liegt.
  2. Jede Schicht trägt einen Hash aus ihrem Inhalt und dem Hash der Schicht darunter.
  3. Bekannter Hash: nichts zu tun. Geänderter Hash: alles Spätere neu.
  4. Was sich selten ändert, kommt in Basis-Layer. Was sich oft ändert, möglichst spät.
  5. Was aufgeräumt werden soll, muss im selben Layer aufgeräumt werden, in dem es entstanden ist.
