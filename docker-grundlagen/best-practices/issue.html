Das Image optimieren

Als Entwicklerin möchte ich wissen, was mein Build jedes Mal kostet, damit ich ihn nicht aus Gewohnheit teuer lasse.

Lernziele

Du…

  • liest aus der Bau-Ausgabe, welche Schritte aus dem Cache kamen und welche nicht.
  • ordnest ein Dockerfile so, dass sich selten Änderndes vorn steht.
  • trennst Bauen und Ausführen in zwei Stufen und machst das Laufzeit-Image damit kleiner.

Definition of Done

  • Du hast die Bauzeit vor dem Umbau nach einer Codeänderung gemessen.
  • Dein Dockerfile kopiert die Abhängigkeitsliste vor dem übrigen Code.
  • Dein Laufzeit-Image aus zwei Stufen ist messbar kleiner als das einstufige.
  • Du hast die Reflexionsfragen schriftlich beantwortet.

Arbeitsschritte

Zuerst messen, dann ändern

Nimm Dein Dockerfile der Webanwendung aus dem vorigen Block. Ändere eine Zeile in app.py – zum Beispiel den Text, den die Anwendung ausgibt.

Bau das Image und stoppe die Zeit:

time docker image build -t meine-webapp:mess-1 .

Hinweis: Lies die Bau-Ausgabe Zeile für Zeile. Welche Schritte sind als CACHED markiert – und welche nicht? Schreib die Zeit auf.

Die Reihenfolge umbauen

Bisher kopiert Dein Dockerfile mit einer Zeile alles hinein und installiert danach die Abhängigkeiten. Teil das auf:

  1. Kopiere zuerst nur requirements.txt.
  2. Lass pip install laufen.
  3. Kopiere danach den Rest der Dateien.

Bau einmal, damit der Cache den neuen Aufbau kennt:

docker image build -t meine-webapp:mess-2 .

Noch einmal messen

Ändere wieder eine Zeile in app.py – dieselbe Art von Änderung wie vorhin.

time docker image build -t meine-webapp:mess-3 .

Hinweis: Vergleiche die beiden Zeiten. Und sieh in der Ausgabe nach, welcher Schritt jetzt CACHED ist, der es vorher nicht war.

Das Laufzeit-Image schlank machen

Dein Image trägt bisher alles mit sich, was zum Bauen nötig war: Python, pip, die Paketlisten. Ein Container daraus braucht nichts davon – er hält es nur vor, bei jedem Start, auf jedem Knoten, in jeder Umgebung. Je weniger ein Container mitschleppt, desto weniger kostet er: beim Verteilen, beim Starten, im Betrieb – und desto weniger Angriffsfläche bringt er mit.

Löschen hilft dagegen nicht: Ein Layer wird nie wieder kleiner. Was hilft, ist eine zweite Stufe – ein Dockerfile darf mehrere FROM haben. In der ersten wird gebaut, in der letzten liegt nur noch das Ergebnis.

Hier wird die Anwendung in der ersten Stufe zu einem ausführbaren Programm gebündelt und in der letzten in ein nacktes Linux gelegt. Leg dafür Dockerfile.multistage an:

FROM python:3.12-slim-bookworm AS bau
WORKDIR /bau
RUN apt-get update \
 && apt-get install -y --no-install-recommends binutils \
 && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt pyinstaller
COPY app.py .
RUN pyinstaller --onefile app.py

FROM debian:12-slim
COPY --from=bau /bau/dist/app /usr/local/bin/app
EXPOSE 8080
CMD ["app"]

docker image build -f Dockerfile.multistage -t meine-webapp:zwei-stufen .

Vergleiche die Größen:

docker image ls

Starte das neue Image gegen Deine Datenbank – mit denselben Umgebungsvariablen wie bisher – und prüfe, dass es dieselbe Antwort liefert.

Hinweis: COPY --from=bau holt eine Datei aus der ersten Stufe in die letzte. Alles Übrige aus der ersten Stufe – Python, pip, pyinstaller, die Zwischenergebnisse – landet nicht im fertigen Image. Es ist derselbe Gedanke wie beim Aufräumen in einer RUN-Zeile, nur konsequenter: Was in der letzten Stufe nie entstanden ist, muss auch nicht gelöscht werden.

Beide Stufen müssen auf derselben Debian-Fassung aufsetzen – hier bookworm. Nimmst Du oben python:3.12-slim (das zeigt inzwischen auf eine neuere Fassung) und unten debian:12-slim, baut das Image zwar, aber der Start scheitert:

Failed to load Python shared library: /lib/.../libm.so.6: version `GLIBC_2.38' not found

Das Programm aus der ersten Stufe erwartet die Bibliotheken, gegen die es gebaut wurde. Das ist kein Sonderfall von Python – es gilt für jedes Programm, das Du in einer Stufe baust und in einer anderen ausführst.

Hinweis: Der Bau dauert hier länger als sonst – pyinstaller packt einen Python-Interpreter mit ein. Das ist der Handel: längere Bauzeit gegen ein kleineres Ergebnis.
