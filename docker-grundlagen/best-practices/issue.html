Die Reihenfolge umbauen und messen

Als Entwicklerin möchte ich wissen, was mein Build jedes Mal kostet, damit ich ihn nicht aus Gewohnheit teuer lasse.

Lernziele

Du…

  • liest aus der Bau-Ausgabe, welche Schritte aus dem Cache kamen und welche nicht.
  • ordnest ein Dockerfile so, dass sich selten Änderndes vorn steht.
  • misst den Unterschied in Sekunden statt ihn zu glauben.
  • erklärst, warum ein Layer, in dem eine Datei gelöscht wird, das Image nicht kleiner macht.

Definition of Done

  • Du hast die Bauzeit vor dem Umbau nach einer Codeänderung gemessen.
  • Dein Dockerfile kopiert die Abhängigkeitsliste vor dem übrigen Code.
  • Du hast die Bauzeit nach dem Umbau nach derselben Codeänderung gemessen.
  • Beide Zahlen stehen in Deiner befehle.md.
  • Du hast die Reflexionsfragen schriftlich beantwortet.

Arbeitsschritte

Zuerst messen, dann ändern

Nimm Dein Dockerfile der Webanwendung aus dem vorigen Block. Ändere eine Zeile in app.py – zum Beispiel den Text, den die Anwendung ausgibt.

Bau das Image und stoppe die Zeit:

time docker image build -t meine-webapp:mess-1 .

Hinweis: Lies die Bau-Ausgabe Zeile für Zeile. Welche Schritte sind als CACHED markiert – und welche nicht? Schreib die Zeit auf.

Die Reihenfolge umbauen

Ordne das Dockerfile so um, dass die Abhängigkeitsliste vor dem übrigen Code kopiert und installiert wird. Der Rest der Anwendung kommt danach.

Hinweis: Die Datei heißt requirements.txt. Überleg Dir, welche Zeile sich häufiger ändert – diese Datei oder Dein Anwendungscode.

Bau einmal, damit der Cache den neuen Aufbau kennt:

docker image build -t meine-webapp:mess-2 .

Noch einmal messen

Ändere wieder eine Zeile in app.py – dieselbe Art von Änderung wie vorhin.

time docker image build -t meine-webapp:mess-3 .

Hinweis: Vergleiche die beiden Zeiten. Und sieh in der Ausgabe nach, welcher Schritt jetzt CACHED ist, der es vorher nicht war.

Löschen macht nicht kleiner

Leg ein kleines Dockerfile daneben an, in einer eigenen Datei Dockerfile.ballast:

FROM debian:12-slim
RUN apt-get update && apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

docker image build -f Dockerfile.ballast -t ballast:zwei-zeilen .

Und jetzt dasselbe in einer Anweisung – ändere Dockerfile.ballast so, dass Installation und Aufräumen in einer RUN-Zeile stehen, verbunden mit &&.

docker image build -f Dockerfile.ballast -t ballast:eine-zeile .

Vergleiche die Größen:

docker images

Hinweis: Wenn der Unterschied kleiner ausfällt, als Du erwartet hast: Sieh Dir an, wie viel die Paketlisten überhaupt ausmachen. Der Mechanismus ist derselbe, egal ob es um Megabyte oder Gigabyte geht.

Bonus (freiwillig): zwei Stufen statt einer

Nur, wenn Du früh fertig bist. Ein Layer wird nie wieder kleiner – also bleibt auch jedes Werkzeug im Image, mit dem gebaut wurde. Ein Dockerfile darf deshalb mehrere FROM haben: In der ersten Stufe wird gebaut, in der letzten liegt nur noch das Ergebnis.

Leg Dockerfile.multistage an:

FROM python:3.12-slim AS bau
WORKDIR /bau
RUN pip install --no-cache-dir pyinstaller
COPY app.py .
RUN pyinstaller --onefile app.py

FROM debian:12-slim
COPY --from=bau /bau/dist/app /usr/local/bin/app
CMD ["app"]

docker image build -f Dockerfile.multistage -t meine-webapp:zwei-stufen .

Vergleiche die Größen:

docker images

Hinweis: COPY --from=bau holt eine Datei aus der ersten Stufe in die letzte. Alles andere aus der ersten Stufe – Python, pip, pyinstaller, die Zwischenergebnisse – landet nicht im fertigen Image. Es ist derselbe Mechanismus wie beim Aufräumen in einer RUN-Zeile, nur konsequenter: Was in der letzten Stufe nie entstanden ist, muss auch nicht gelöscht werden.

Hinweis: Der Bau dauert hier länger als sonst – pyinstaller packt einen Python-Interpreter mit ein. Das ist der Handel: längere Bauzeit gegen ein kleineres Ergebnis.

Reflexionsfragen

  • Wie viel Zeit hat der Umbau gespart, und wobei genau?
  • Welche Änderung macht jetzt noch den ganzen Build ungültig – und warum ist das richtig so?
  • Warum ist das Image mit zwei RUN-Zeilen größer, obwohl am Ende dieselben Dateien fehlen?
  • Was ändert sich an Deinem Image, wenn Du nur den Startbefehl (CMD) anfasst? Wird dabei eine Schicht neu gebaut?
  • Falls Du den Bonus gemacht hast: Was liegt im Image mit zwei Stufen nicht mehr drin – und warum hättest Du das mit einer einzelnen RUN-Zeile nicht wegbekommen?
