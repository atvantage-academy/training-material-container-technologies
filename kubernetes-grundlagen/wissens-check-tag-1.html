      Kubernetes – Grundlagen für Entwickler/Wissens-Check: Tag 1

      Wissens-Check: Tag 1

      Sechzehn Fragen als Rückblick auf den ersten Tag. Sie prüfen, was Du wiedererkennst – das ist weniger, als Du kannst, und mehr, als Du glaubst. Es gibt keine Note und keine Auswertung im Kurs; die Antworten siehst nur Du.

      Lies bei jeder Antwort auch die Begründung, wenn Du danebengegriffen hast. Sie ist der eigentliche Inhalt dieser Seite.

      1. Kubernetes gibt es nicht nur in einer Fassung.

        Was ist OpenShift im Verhältnis zu Kubernetes?

        • Eine Distribution von Kubernetes mit zusätzlichen Funktionen.

        • Eine eigenständige Plattform, die mit Kubernetes nichts teilt.

        • Eine Erweiterung, die Kubernetes um OpenShift-Funktionen ergänzt.

        • Ein anderer Name für dasselbe Produkt, nur unter einer Marke.

      2. Es gibt mehrere Wege, eine Ressource im Cluster anzulegen.

        Welche Aussage trifft zu?

        • Sowohl kubectl create als auch kubectl apply -f legen Ressourcen an.

        • Nur über eine grafische Oberfläche, weil Kubernetes grafisch bedient wird.

        • Nur mit kubectl create, weil kubectl apply ausschließlich liest.

        • Nur, indem man YAML-Dateien direkt auf einen Worker Node kopiert.

      3. Du hast ein Deployment mit kubectl apply -f deployment.yaml angelegt und änderst nun das Image-Tag in der Datei.

        Was passiert beim erneuten kubectl apply -f deployment.yaml?

        • Kubernetes aktualisiert das bestehende Deployment.

        • Es gibt einen Fehler, weil es das Deployment schon gibt.

        • Es entsteht ein zweites Deployment mit gleichem Namen.

        • Das Deployment wird gelöscht und komplett neu angelegt.

      4. Du führst kubectl apply -f deployment.yaml direkt ein zweites Mal aus, ohne die Datei zu ändern.

        Was passiert?

        • Nichts – der gewünschte Zustand ist schon erreicht.

        • Alle Pods des Deployments werden neu gestartet.

        • Es kommt ein Fehler, weil die Ressource existiert.

        • Kubernetes legt eine Sicherung des alten Zustands an.

      5. Du änderst in der Datei eines bestehenden Deployments den Namen und wendest sie erneut an:

        # vorher
metadata:
  name: recipes-backend

# nachher
metadata:
  name: recipes-api

        Was passiert?

        • Es entsteht ein zweites Deployment; das alte läuft weiter.

        • Das bestehende Deployment wird in recipes-api umbenannt.

        • Es gibt einen Fehler, weil sich Namen nicht ändern dürfen.

        • Das alte Deployment wird gelöscht und durch das neue ersetzt.

      6. Du willst ein Deployment anlegen, das es noch nicht gibt.

        Worin unterscheiden sich kubectl create und kubectl apply?

        • create scheitert an Vorhandenem, apply legt an oder ändert.

        • create ist für Deployments da, apply nur für Services.

        • Es gibt keinen Unterschied, beide Befehle sind nur Aliase füreinander.

        • apply ist veraltet und wird durch create ganz ersetzt.

      7. Kubernetes wird oft „deklarativ“ genannt.

        Was ist damit gemeint?

        • Ich beschreibe den Zielzustand, Kubernetes stellt ihn her und hält ihn.

        • Ich gebe Schritt für Schritt vor, welcher Container wann und wo startet.

        • Kubernetes fragt vor jedem Schritt nach, ob es weitermachen soll.

        • Alle Befehle an den Cluster werden lückenlos mitprotokolliert.

      8. Ein Unternehmen überlegt, seine Anwendungen auf Kubernetes zu betreiben.

        Welche zwei Vorteile bringt Kubernetes vor allem?

        • Verteilung auf mehrere Maschinen und hohe Verfügbarkeit.

        • Schnellere Programmiersprachen und leistungsfähigere Datenbanken.

        • Automatische Code-Reviews und Genehmigungen für Deployments.

        • Garantiert geringere Kosten in der Cloud und schnellere Netze.

      9. Du hast die Dateien service.yaml, ingress.yaml und deployment.yaml.

        Spielt die Reihenfolge eine Rolle, wenn Du sie mit kubectl apply -f anwendest?

        • Nein – der Cluster erreicht den Zielzustand in jeder Reihenfolge.

        • Ja, das Deployment muss zuerst da sein, sonst gibt es Fehler.

        • Ja, der Ingress muss zuerst da sein, damit der Service ihn findet.

        • Ja, die Dateien müssen alphabetisch sortiert angewendet werden.

      10. Ein Pod startet nicht und bleibt im Status CrashLoopBackOff.

        Womit untersuchst Du den Fehler?

        • Mit kubectl describe pod und kubectl logs.

        • Mit kubectl delete pod und einem erneuten Versuch.

        • Mit einem Neustart des ganzen Clusters über kubectl.

        • Gar nicht – Fehler in Kubernetes lassen sich nur erraten.

      11. Du legst ein Deployment an, das auf ein Image in einer Registry verweist.

        Wann wird das Image heruntergeladen?

        • Wenn ein Pod auf einem Node startet, dem das Image fehlt.

        • Sofort bei kubectl apply -f, noch bevor es einen Pod gibt.

        • Gar nicht – es muss von Hand auf jeden Node kopiert werden.

        • Einmal beim Einrichten des Clusters und danach nie wieder.

      12. Bei einem neuen Image-Tag ersetzt Kubernetes die alten Pods eines Deployments durch neue.

        Was beschreibt die Strategie RollingUpdate?

        • Alte Pods werden schrittweise ersetzt, die App bleibt erreichbar.

        • Alle alten Pods stoppen sofort, danach starten die neuen.

        • Das Update läuft rückwärts ab, vom letzten Pod bis hin zum ersten.

        • Das Update wird automatisch auf das nächste Wochenende gelegt.

      13. Ein Deployment hat replicas: 3. Der Worker Node, auf dem einer der Pods lief, fällt aus.

        Was passiert?

        • Kubernetes startet den fehlenden Pod auf einem anderen Node neu.

        • Nichts – es laufen zwei Pods weiter, bis jemand eingreift.

        • Der ganze Cluster fährt herunter, bis der Node repariert ist.

        • Die Anwendung ist komplett offline, bis der Node wieder verfügbar ist.

      14. In Kubernetes arbeiten verschiedene Arten von Ressourcen zusammen.

        Was ist die Aufgabe eines Service?

        • Eine stabile Adresse, die Anfragen auf die passenden Pods verteilt.

        • Er startet und stoppt die Container auf den Worker Nodes.

        • Er speichert Konfigurationswerte wie die Adresse der Datenbank.

        • Er macht die Anwendung von außerhalb des Clusters direkt erreichbar.

      15. Du möchtest Deine Anwendung von außerhalb des Clusters erreichbar machen.

        Welche Ressource brauchst Du dafür?

        • Einen Ingress, der einen Hostnamen auf den Service lenkt.

        • Ein zweites Deployment mit dem Label external: true.

        • Einen Pod, der seinen Container auf Port 443 öffnet.

        • Eine ConfigMap, in der die externe Adresse eingetragen ist.

      16. Nach dem Anlegen eines Deployments zeigt der Pod den Status ImagePullBackOff.

        Was bedeutet das?

        • Das Image ließ sich nicht aus der Registry laden.

        • Der Pod läuft, hat aber Probleme mit der Leistung.

        • Das Image ist zu groß für den Speicher des Clusters.

        • Ein anderer Pod benutzt das Image gerade und sperrt es.
