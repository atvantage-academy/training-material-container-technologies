    Eine PostgreSQL-Datenbank bereitstellen

    User Story

    Als Entwickler:in möchte ich eine PostgreSQL-Datenbank in Kubernetes betreiben, deren Konfiguration sauber und sicher bereitgestellt wird, damit das Backend später auf eine echte Datenbank umgestellt werden kann.

    Lernziele
    • Du betreibst eine Datenbank als Workload in Kubernetes.
    • Du stellst die Konfiguration einer Anwendung von außen bereit – getrennt nach sensiblen und unkritischen Werten.
    • Du bringst eine Datei in einen Container, die nicht Teil des Images ist.
    Definition of Done
    • kubectl get pods zeigt einen PostgreSQL-Pod im Status Running, gestartet mit den geforderten Parametern.
    • Benutzer und Passwort stehen in einem Secret; das Deployment verweist nur darauf.
    • Der Datenbankname steht in einer ConfigMap; das Deployment verweist nur darauf.
    • Die Logs des Pods zeigen, dass init.sql ausgeführt wurde und die Tabellen angelegt sind.
    • PostgreSQL schreibt seine Daten in ein eigenes Verzeichnis (PGDATA auf einem Volume).
    • Du hast die Kontrollfragen beantwortet

    Hinweis: Diese Übung beschreibt bewusst nur das Ziel und die nötigen Parameter – nicht den Weg. Überleg selbst, mit welchen Kubernetes-Ressourcen Du das umsetzt.

    Arbeitsschritte

    Die Datenbank bereitstellen

    Benötigt wird ein Pod mit einer PostgreSQL-Datenbank, der diese Parameter erfüllt:

    Parameter Wert
    Image postgres:17-alpine
    Port 5432
    POSTGRES_USER (Umgebungsvariable) frei wählbar, etwa recipes
    POSTGRES_PASSWORD (Umgebungsvariable) frei wählbar, etwa recipes-secret-pw
    POSTGRES_DB (Umgebungsvariable) recipes
    Init-SQL Datei init.sql im Verzeichnis /docker-entrypoint-initdb.d/

    Dabei gilt:

    • Die Zugangsdaten (POSTGRES_USER, POSTGRES_PASSWORD) stehen nicht im Klartext im Deployment.
    • Der Datenbankname (POSTGRES_DB) ist unkritisch, soll aber ebenfalls von außen konfigurierbar sein.

    Das Init-SQL, das beim ersten Start das Schema anlegt:

    CREATE TABLE recipes (
    id          VARCHAR(36)   PRIMARY KEY,
    name        VARCHAR(100)  NOT NULL,
    img         VARCHAR(255),
    servings    INTEGER       NOT NULL,
    lastEdited  TIMESTAMP WITH TIME ZONE,
    duration    INTEGER       NOT NULL,
    difficulty  VARCHAR(10),
    preparation VARCHAR(2000) NOT NULL
);

CREATE TABLE ingredients (
    id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name      VARCHAR(100) NOT NULL,
    quantity  DOUBLE PRECISION NOT NULL,
    unit      VARCHAR(20)  NOT NULL,
    recipe_id VARCHAR(36)  REFERENCES recipes(id) ON DELETE CASCADE
);

    Hinweis – Init-SQL in den Container bringen: Das offizielle PostgreSQL-Image führt beim ersten Start alle *.sql-Dateien aus /docker-entrypoint-initdb.d/ aus. Eine Datei, die nicht im Image liegt, legst Du als ConfigMap an und hängst sie als Volume ein. Das Muster, abstrakt:

    # Ausschnitt aus dem Template eines Deployments
spec:
  containers:
    - name: my-app
      image: my-image
      volumeMounts:
        - name: my-files
          mountPath: /pfad/im/container
  volumes:
    - name: my-files
      configMap:
        name: meine-configmap

    Hinweis – kein persistenter Speicher nötig: Für diese Übung genügt flüchtiger Speicher. Produktionsreif wäre ein StatefulSet mit PersistentVolumeClaim – siehe PostgreSQL auf Kubernetes.

    Den Zwischenstand prüfen

    Wende Deine Ressourcen an und sieh Dir Status und Logs an:

    kubectl get pods

    kubectl logs <postgres-pod-name>

    In den Logs sollte die Ausführung von init.sql zu sehen sein.

    Achtung, abhängig vom Cluster: Startet der Cluster Container mit einer zufällig vergebenen User-ID – so der bereitgestellte Cluster, siehe Schulungsumgebung –, scheitert der Start hier mit einem Rechtefehler auf dem Datenverzeichnis:

    initdb: error: could not change permissions of directory "/var/lib/postgresql/data": Operation not permitted

    Auf Minikube tritt das meist nicht auf. Der nächste Schritt löst das Problem sauber – und bereitet den persistenten Speicher vor.

    PostgreSQL ein eigenes Datenverzeichnis geben

    Gib PostgreSQL ein eigenes, beschreibbares Datenverzeichnis. Ergänze im Deployment drei Dinge:

    1. die Umgebungsvariable PGDATA auf ein Unterverzeichnis,
    2. einen volumeMount für die Daten,
    3. das zugehörige volume – hier ein emptyDir, flüchtig, für diese Übung genug.
        spec:
      containers:
        - name: postgres
          image: postgres:17-alpine
          # Ports und Verweise auf Secret und ConfigMap wie zuvor …
          env:
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
      volumes:
        - name: data
          emptyDir: {}

    Warum das hilft: Das leere, beschreibbare Volume data liegt auf /var/lib/postgresql/data. Mit PGDATA=/var/lib/postgresql/data/pgdata legt PostgreSQL sein Datenverzeichnis in ein selbst angelegtes Unterverzeichnis – das gehört ihm, und dessen Rechte darf es setzen.

    Wende das Deployment erneut an und prüf Status und Logs:

    kubectl apply -f postgres-deployment.yaml

    kubectl get pods

    kubectl logs <postgres-pod-name>

    Musterlösung

    Musterlösung aufdecken – erst, wenn Du es selbst versucht hast

    Eine mögliche Lösung – als YAML und als Befehle. Es gibt andere gültige Wege; wichtig ist, dass die geforderten Parameter erfüllt sind.

    Secret für die Zugangsdaten

    Deklarativ – postgres-secret.yaml:

    apiVersion: v1
kind: Secret
metadata:
  name: postgres-secret
type: Opaque
stringData:
  POSTGRES_USER: recipes
  POSTGRES_PASSWORD: recipes-secret-pw

    kubectl apply -f postgres-secret.yaml

    stringData nimmt Klartext entgegen; Kubernetes kodiert ihn selbst nach Base64. Unter data müsstest Du die Werte selbst kodieren.

    Oder imperativ:

    kubectl create secret generic postgres-secret --from-literal=POSTGRES_USER=recipes --from-literal=POSTGRES_PASSWORD=recipes-secret-pw

    Noch sauberer ist ein zufälliges Passwort, das in keiner Datei landet. Lass Dir eines erzeugen:

    openssl rand -hex 16

    und setz die Ausgabe statt recipes-secret-pw in den Befehl oben ein. Das Backend liest das Passwort später aus demselben Secret – niemand muss es kennen.

    Gut zu wissen: Base64 ist keine Verschlüsselung. Wer das Secret lesen darf, kann den Wert dekodieren. Mehr dazu: Sind Secrets sicher?

    ConfigMap für den Datenbanknamen

    Deklarativ – postgres-config.yaml:

    apiVersion: v1
kind: ConfigMap
metadata:
  name: postgres-config
data:
  POSTGRES_DB: recipes

    kubectl apply -f postgres-config.yaml

    Oder imperativ:

    kubectl create configmap postgres-config --from-literal=POSTGRES_DB=recipes

    ConfigMap für das Init-SQL

    Am einfachsten aus der Datei init.sql:

    kubectl create configmap postgres-init-sql --from-file=init.sql

    Oder deklarativ mit eingebettetem Inhalt – postgres-init-sql.yaml:

    apiVersion: v1
kind: ConfigMap
metadata:
  name: postgres-init-sql
data:
  init.sql: |
    CREATE TABLE recipes (
        id          VARCHAR(36)   PRIMARY KEY,
        name        VARCHAR(100)  NOT NULL,
        img         VARCHAR(255),
        servings    INTEGER       NOT NULL,
        lastEdited  TIMESTAMP WITH TIME ZONE,
        duration    INTEGER       NOT NULL,
        difficulty  VARCHAR(10),
        preparation VARCHAR(2000) NOT NULL
    );

    CREATE TABLE ingredients (
        id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
        name      VARCHAR(100) NOT NULL,
        quantity  DOUBLE PRECISION NOT NULL,
        unit      VARCHAR(20)  NOT NULL,
        recipe_id VARCHAR(36)  REFERENCES recipes(id) ON DELETE CASCADE
    );

    kubectl apply -f postgres-init-sql.yaml

    Deployment

    postgres-deployment.yaml:

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres
spec:
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:17-alpine
          ports:
            - containerPort: 5432
          env:
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          envFrom:
            - secretRef:
                name: postgres-secret
            - configMapRef:
                name: postgres-config
          volumeMounts:
            - name: init-sql
              mountPath: /docker-entrypoint-initdb.d
            - name: data
              mountPath: /var/lib/postgresql/data
      volumes:
        - name: init-sql
          configMap:
            name: postgres-init-sql
        - name: data
          emptyDir: {}

    kubectl apply -f postgres-deployment.yaml

    Worauf es ankommt:

    • envFrom übernimmt alle Schlüssel aus Secret und ConfigMap als Umgebungsvariablen (POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB). Alternativ einzeln mit env und valueFrom.secretKeyRef – das brauchst Du in der nächsten Übung.
    • init-sql als Volume landet unter /docker-entrypoint-initdb.d; das Image führt *.sql nur beim ersten Start aus, solange das Datenverzeichnis leer ist.
    • PGDATA und ein eigenes Volume data: Ohne beide scheitert der Start auf Clustern mit zufälliger User-ID. Persistent ist das noch nicht – das emptyDir lebt so lange wie der Pod.

    Prüfen

    kubectl get pods

    # Ist die Ausführung von init.sql zu sehen?
kubectl logs deployment/postgres

    # Gegenprobe in der Datenbank: die Tabellen auflisten
kubectl exec deployment/postgres -- psql -U recipes -d recipes -c '\dt'

    Zum Weiterlesen: emptyDir und der Weg zur Persistenz

    Ein emptyDir ist ein leeres Verzeichnis auf dem Node, auf dem der Pod läuft. Es lebt so lange wie der Pod: Startet nur der Container neu (Absturz, Liveness-Probe), bleiben die Daten; wird der Pod gelöscht oder zieht er um, sind sie weg. Das unterscheidet es von einem PersistentVolume, das unabhängig vom Pod existiert.

    Würde PostgreSQL direkt in die Wurzel des Volumes schreiben, scheiterte es in zwei Fällen: auf Clustern mit zufälliger User-ID, weil diese die Rechte der Wurzel nicht ändern darf; und bei manchen PersistentVolumes, deren Wurzel nicht leer ist (etwa lost+found). Das Unterverzeichnis aus PGDATA löst beides.

    Für persistenten Speicher wird später nur das emptyDir durch einen persistentVolumeClaim ersetzt – volumeMount und PGDATA bleiben, wie sie sind.

    Reflexionsfragen

    • Wie hast Du verhindert, dass die Zugangsdaten im Klartext im Deployment stehen? Welche Ressource ist dafür gedacht?
    • Warum gehören Datenbankname und Zugangsdaten in unterschiedliche Ressourcentypen?
    • Wie sicher ist ein Kubernetes-Secret wirklich?
    • Warum bindest Du das Init-SQL von außen ein, statt es ins Image zu packen?
    • Worin unterscheidet sich envFrom (ganze Ressource) von einzelnen env-Einträgen mit valueFrom?
    • Inwiefern ist dieses PostgreSQL-Setup nicht produktionsreif?
