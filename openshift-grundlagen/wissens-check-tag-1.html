    OpenShift – Grundlagen für Entwickler/Wissens-Check: Tag 1

    Wissens-Check: Tag 1

    Sechzehn Fragen als Rückblick auf den ersten Tag: warum es Kubernetes gibt, wie OpenShift dazu steht, was oc apply tut und wie Du Fehler findest. Es gibt keine Note und keine Auswertung im Kurs; die Antworten siehst nur Du.

    Lies bei jeder Antwort auch die Begründung, wenn Du danebengegriffen hast. Sie ist der eigentliche Inhalt dieser Seite.

    1. OpenShift wird oft „Enterprise Kubernetes“ genannt.

      Wie stehen OpenShift und Kubernetes zueinander?

      • OpenShift ist eine Kubernetes-Distribution mit Zusätzen wie Routes und SCCs.

      • OpenShift ist eine eigenständige Plattform, die Kubernetes gar nicht verwendet.

      • Kubernetes ist eine abgespeckte Erweiterung, die auf OpenShift aufsetzt.

      • Beides sind nur zwei Markennamen für genau dasselbe Produkt am Markt.

    2. Im Cluster gibt es mehrere Wege, eine Ressource anzulegen.

      Welche Aussage trifft zu?

      • Es geht über die Web Console, mit oc create oder mit oc apply -f.

      • Es geht nur über die Web Console, weil der Cluster grafisch bedient wird.

      • Es geht nur mit YAML-Dateien, die man per oc get an den Cluster schickt.

      • Es geht nur mit oc create, denn oc apply liest die Ressourcen nur aus.

    3. Du hast ein Deployment mit oc apply -f deployment.yaml angelegt. Jetzt änderst Du in der Datei das Image-Tag und wendest sie erneut an.

      Was passiert?

      • Der Cluster erkennt die Änderung und aktualisiert das bestehende Deployment.

      • Es gibt einen Fehler, weil ein Deployment dieses Namens bereits existiert.

      • Es entsteht ein zweites Deployment mit gleichem Namen neben dem ersten.

      • Das bestehende Deployment wird erst gelöscht und dann komplett neu angelegt.

    4. Du hast gerade oc apply -f deployment.yaml ausgeführt und führst denselben Befehl ohne Änderung an der Datei noch einmal aus.

      Was passiert?

      • Nichts – der gewünschte Zustand ist im Cluster bereits hergestellt.

      • Alle Pods des Deployments werden nacheinander einmal neu gestartet.

      • Es gibt eine Fehlermeldung, weil die Ressource schon existiert.

      • Der Cluster legt eine Sicherung des vorherigen Zustands an.

    5. Du hast das Deployment recipes-backend mit oc apply -f deployment.yaml angelegt. Jetzt änderst Du in der Datei den Namen:

      # vorher
metadata:
  name: recipes-backend

# nachher
metadata:
  name: recipes-api

      Was passiert beim erneuten oc apply -f deployment.yaml?

      • Ein zweites Deployment recipes-api entsteht, das alte bleibt bestehen.

      • Das bestehende Deployment wird von recipes-backend in recipes-api umbenannt.

      • Es gibt einen Fehler, weil sich der Name einer Ressource nicht ändern darf.

      • Das alte Deployment wird gelöscht und durch recipes-api ersetzt.

    6. Du willst ein Deployment anlegen, das es noch nicht gibt.

      Was unterscheidet oc create von oc apply?

      • create legt nur neu an, apply legt an oder ändert, was schon da ist.

      • create ist für Deployments gedacht, apply dagegen für Services.

      • Es gibt keinen Unterschied, die beiden Befehle sind nur Aliase füreinander.

      • apply ist veraltet und wird von create vollständig abgelöst.

    7. Kubernetes wird oft als „deklarativ“ beschrieben.

      Was bedeutet das?

      • Du beschreibst den Zielzustand, der Cluster stellt ihn her und hält ihn.

      • Du gibst Schritt für Schritt vor, welcher Container wann startet.

      • Der Cluster fragt vor jedem einzelnen Schritt nach, ob er weitermachen soll.

      • Jeder Befehl an den Cluster wird automatisch mitprotokolliert.

    8. Ein Unternehmen überlegt, seine Anwendungen auf Kubernetes zu betreiben.

      Was spricht vor allem dafür?

      • Verteilung auf mehrere Maschinen und Ausfallsicherheit durch Selbstheilung.

      • Schnellere Programmiersprachen und leistungsfähigere Datenbanken im eigenen Code.

      • Automatische Code-Reviews und Freigaben jedes Deployments durch das Team.

      • Garantiert niedrigere Kosten in der Cloud und eine schnellere Anbindung.

    9. Du hast drei YAML-Dateien: service.yaml, route.yaml und deployment.yaml.

      Spielt es eine Rolle, in welcher Reihenfolge Du sie mit oc apply -f anlegst?

      • Nein – der Cluster nähert sich dem Zielzustand in jeder Reihenfolge an.

      • Ja – das Deployment muss zuerst angelegt sein, sonst gibt es einen Fehler.

      • Ja – die Route muss zuerst existieren, damit der Service sie finden kann.

      • Ja – die Dateien müssen alphabetisch sortiert angewendet werden, also so.

    10. Ein Pod startet nicht und bleibt im Status CrashLoopBackOff.

      Womit findest Du die Ursache?

      • oc describe pod für die Events, oc logs für die Ausgabe der Anwendung.

      • Mit oc delete pod den Pod löschen und dann einfach noch einmal versuchen.

      • Mit oc restart cluster den ganzen Cluster neu starten und dann abwarten.

      • Gar nicht – Fehler im Cluster lassen sich nur durch Ausprobieren eingrenzen.

    11. Du legst ein Deployment an, das auf ein Image in einer Registry verweist.

      Wann wird das Image heruntergeladen?

      • Wenn ein Pod auf einen Node kommt, auf dem das Image noch fehlt.

      • Sofort bei oc apply -f, noch bevor überhaupt ein Pod entsteht.

      • Gar nicht – das Image muss vorher von Hand auf jeden Node kopiert werden.

      • Einmal beim Einrichten des Clusters und danach nie wieder.

    12. Du aktualisierst ein Deployment, etwa mit einem neuen Image-Tag.

      Was beschreibt die Strategie RollingUpdate?

      • Alte Pods werden schrittweise durch neue ersetzt, ohne Ausfall.

      • Alle alten Pods werden sofort beendet, danach starten die neuen.

      • Das Update läuft rückwärts, also vom letzten Pod bis zum ersten.

      • Das Update wird gesammelt und erst zu einer festen Uhrzeit ausgeführt.

    13. Dein Deployment hat replicas: 3. Ein Worker Node, auf dem einer der Pods lief, fällt aus.

      Was passiert?

      • Der Cluster startet von selbst einen neuen Pod auf einem anderen Node.

      • Nichts – die Anwendung läuft mit zwei Pods weiter, bis jemand eingreift.

      • Der ganze Cluster fährt herunter, weil ein Node nicht mehr erreichbar ist.

      • Die Anwendung ist komplett offline, bis der Node wieder repariert ist.

    14. Im Cluster arbeiten verschiedene Ressourcentypen zusammen.

      Was ist die Aufgabe eines Service?

      • Er ist eine stabile Adresse vor wechselnden Pods und verteilt Anfragen.

      • Er startet und stoppt die Container eines Deployments nach Bedarf.

      • Er speichert Konfigurationswerte wie die Adresse einer Datenbank.

      • Er macht die Anwendung für Browser außerhalb des Clusters direkt erreichbar.

    15. Deine Anwendung soll aus dem Internet erreichbar sein.

      Welche OpenShift-Ressource brauchst Du dafür?

      • Eine Route, die auf den Service der Anwendung verweist.

      • Ein zweites Deployment mit dem Label external: true.

      • Einen Pod, dessen Container auf dem Port 443 lauscht.

      • Eine ConfigMap, in der die externe Adresse eingetragen ist.

    16. Beim Anlegen eines Pods siehst Du den Status ImagePullBackOff.

      Was bedeutet das?

      • Das Image ließ sich nicht laden – etwa wegen eines falschen Namens oder Tags.

      • Der Container läuft bereits, antwortet aber spürbar langsamer als sonst üblich.

      • Das Image ist zu groß für den Speicher, den der Cluster dafür bereitstellt.

      • Ein anderer Pod verwendet dasselbe Image gerade und sperrt es für alle.

    Hakt es bei einer Frage? Die Visualisierungen Was ist Kubernetes? und Kubernetes-Ressourcen sowie der Spickzettel: kubectl und oc zeigen die Zusammenhänge noch einmal im Überblick.
