    Das Backend auf PostgreSQL umstellen

    User Story

    Als Entwickler:in möchte ich das Backend von der eingebauten H2-Datenbank auf die PostgreSQL-Datenbank umstellen, damit die Daten in einer echten Datenbank liegen und einen Neustart des Backends überstehen.

    Lernziele
    • Du stellst ein bestehendes Deployment auf ein anderes Image-Tag um.
    • Du kombinierst Umgebungsvariablen aus einem Secret mit festen Werten.
    • Du machst eine Anwendung über einen Service unter einem stabilen DNS-Namen im Cluster erreichbar.
    Definition of Done
    • Der Service postgres existiert und zeigt auf den Pod der Datenbank (Port 5432).
    • Das Backend-Deployment nutzt das Image ralfueberfuhr/recipes-backend:latest.
    • DB_USER und DB_PASSWORD kommen über secretKeyRef aus dem Secret der Datenbank.
    • Ein über die API angelegtes Rezept ist nach einem Neustart des Backends weiterhin abrufbar.
    • Du hast die Kontrollfragen beantwortet

    Arbeitsschritte

    Du arbeitest mit dem Backend aus „Das Backend deployen“ und der Datenbank aus „Eine PostgreSQL-Datenbank bereitstellen“ weiter.

    Die Datenbank über einen Service erreichbar machen

    Damit das Backend die Datenbank über einen stabilen Namen statt über eine wechselnde Pod-IP erreicht, braucht sie einen Service – nach demselben Muster wie beim Backend:
    Name postgres
    Selektor app: postgres
    Port 5432

    Hinweis: Der Name des Service ist zugleich der Hostname, unter dem die Datenbank im Cluster erreichbar ist. Du verwendest ihn gleich in der Adresse der Datenbank.

    Prüf, ob der Service den Pod gefunden hat – unter Endpoints muss eine IP-Adresse stehen:

    oc describe service postgres

    Das Image-Tag ändern

    Ändere im Deployment des Backends das Tag von latest-dev auf latest. Diese Fassung erwartet eine PostgreSQL-Datenbank:

    image: ralfueberfuhr/recipes-backend:latest

    Die Umgebungsvariablen setzen

    Ergänze im Deployment des Backends drei Umgebungsvariablen:

    Variable Wert
    DB_URL jdbc:postgresql://postgres:5432/recipes
    DB_USER aus dem Secret der Datenbank, Schlüssel POSTGRES_USER
    DB_PASSWORD aus dem Secret der Datenbank, Schlüssel POSTGRES_PASSWORD

    postgres in der JDBC-URL ist der Name des Service aus dem ersten Schritt; der Cluster löst ihn als DNS-Namen auf.

    Die Variablen im Backend heißen anders als die Schlüssel im Secret – deshalb holst Du jeden Wert einzeln. So sieht das für einen Wert aus:

    env:
  - name: DB_USER
    valueFrom:
      secretKeyRef:
        name: postgres-secret
        key: POSTGRES_USER

    Hinweis: Heißt Dein Secret anders als postgres-secret, setz Deinen Namen ein.

    Das Deployment anwenden und prüfen

    oc apply -f backend-deployment.yaml

    oc get pods

    Sieh in den Logs nach, ob das Backend die Datenbank erreicht:

    oc logs <backend-pod-name>

    Hinweis: Startet das Backend, bevor die Datenbank erreichbar ist, landet es kurz in CrashLoopBackOff und versucht es dann erneut. Sieh in diesem Fall in die Events:

    oc describe pod <backend-pod-name>

    Einen Neustart überstehen

    Leg über die API ein Rezept an:

    curl -i -X POST https://<backend-route-host>/recipes -H "Content-Type: application/json" -d '{"name":"Test","servings":2,"duration":10,"ingredients":[{"name":"Tomate","quantity":1,"unit":"pieces"}],"preparation":"Kochen."}'

    Starte das Backend neu:

    oc rollout restart deployment/recipes-backend

    Warte, bis der neue Pod läuft (oc get pods), und ruf die Rezepte ab:

    curl -i https://<backend-route-host>/recipes

    Dein Rezept ist noch da – es liegt jetzt in PostgreSQL, nicht mehr im Speicher des Backends.

    Reflexionsfragen

    • Braucht die Datenbank auch eine Route?
    • Warum funktioniert hier der interne Name postgres, während das Frontend die Route des Backends brauchte?
    • Was passiert mit Deinen Rezepten, wenn der Pod der Datenbank neu startet?
