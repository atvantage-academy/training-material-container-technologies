    Die Datenbank als Helm Chart

    User Story

    Als Entwickler:in möchte ich die Datenbank als Helm Chart paketieren und dabei die Helm-Kommandozeile kennenlernen, damit ich sie mit einem Befehl und je Umgebung passenden Werten installieren kann.

    Lernziele
    • Du beschreibst den Aufbau eines Helm Charts anhand dessen, was helm create erzeugt.
    • Du überführst vorhandene Manifeste in Templates eines Charts.
    • Du lagerst Werte in die values.yaml aus und verwendest sie in Templates.
    • Du prüfst ein Chart mit helm lint und helm template und installierst es mit helm install.
    Definition of Done
    • Das Chart recipes-db enthält die Ressourcen der Datenbank als Templates.
    • Image-Tag, Anzahl der Replicas, Datenbankname, Benutzer und Passwort kommen aus der values.yaml.
    • helm template mit -f values-prod.yaml erzeugt sichtbar andere Manifeste als ohne.
    • helm list zeigt das Release recipes-db, und der Pod der Datenbank steht auf Running.
    • Du hast die Kontrollfragen beantwortet

    Arbeitsschritte

    Hinweis: Prüf zuerst, ob helm in Deiner Shell verfügbar ist: helm version. Helm nutzt dieselbe Anmeldung und dasselbe Projekt wie oc.

    Die bisherigen Ressourcen aufräumen

    Ab jetzt übernimmt Helm das Deployment. Damit es keine Konflikte mit den bisher von Hand angelegten Objekten gibt, räumst Du auf. Deine YAML-Dateien bleiben erhalten – nur die Objekte im Cluster werden gelöscht.

    oc delete deployment recipes-backend recipes-frontend postgres

    oc delete service recipes-backend recipes-frontend postgres

    oc delete route recipes-backend recipes-frontend

    oc delete configmap frontend-config postgres-config postgres-init-sql

    oc delete secret postgres-secret

    # Nur, falls Du in „Persistenten Speicher einrichten“ einen PVC angelegt hast
oc delete pvc postgres-data

    Prüf, ob alles weg ist:

    oc get all

    Hinweis: Fehlermeldungen zu Objekten, die es nicht (mehr) gibt, kannst Du ignorieren. Hast Du Deine Ressourcen anders benannt, setz Deine Namen ein.

    Ein erstes Chart erzeugen

    Leg einen gemeinsamen Ordner für alle Charts an und wechsle hinein:

    mkdir helm-charts

    cd helm-charts

    helm create recipes-db

    helm create erzeugt ein vollständiges Beispiel-Chart. Sieh Dir die erzeugten Dateien an – Chart.yaml, values.yaml und den Ordner templates/. Das ist der beste Einstieg in den Aufbau eines Charts.

    Die Chart.yaml anpassen

    Ersetze den Inhalt von recipes-db/Chart.yaml:

    apiVersion: v2
name: recipes-db
description: PostgreSQL-Datenbank für die Rezeptverwaltung
version: 0.1.0
appVersion: "17"
type: application

    Die Manifeste der Datenbank als Templates übernehmen

    Lösch alle erzeugten Dateien im Ordner recipes-db/templates/ – auch NOTES.txt, _helpers.tpl und den Ordner tests/. Leg stattdessen Deine Manifeste der Datenbank dort ab: Secret, ConfigMap für den Datenbanknamen, ConfigMap für das Init-SQL, Deployment und Service.

    Hinweis: Verweist Dein Deployment auf den PVC postgres-data, gehört auch postgres-pvc.yaml in den Ordner templates/ – sonst wartet der Pod auf einen Claim, den es nicht mehr gibt.

    Leere die erzeugte recipes-db/values.yaml vorerst – sie bekommt gleich eigene Werte.

    Das Chart prüfen

    Prüf das Chart auf Fehler und sieh Dir die erzeugten Manifeste an, ohne etwas zu installieren:

    helm lint ./recipes-db

    helm template test-release ./recipes-db

    Werte in die values.yaml auslagern

    Jetzt kommt der eigentliche Gewinn: Ersetze fest eingetragene Werte in den Templates durch Verweise auf die values.yaml. Fang mit ein paar wichtigen Werten an, nicht mit allen auf einmal.

    recipes-db/values.yaml:

    image:
  repository: postgres
  tag: "17-alpine"
replicas: 1
database:
  name: recipes
  user: recipes
  password: recipes-secret-pw

    Im Template des Deployments ersetzt Du dann zum Beispiel:

    # Vorher:
image: postgres:17-alpine

# Nachher:
image: {{ .Values.image.repository }}:{{ .Values.image.tag }}

    Und im Secret (Helm kann Klartext über stringData übergeben):

    stringData:
  POSTGRES_USER: {{ .Values.database.user }}
  POSTGRES_PASSWORD: {{ .Values.database.password }}

    Verwende genauso .Values.replicas im Deployment und .Values.database.name in der ConfigMap. Prüf nach jeder Änderung erneut:

    helm lint ./recipes-db

    helm template test-release ./recipes-db

    Eine zweite Umgebung beschreiben

    Der Nutzen zeigt sich, wenn dieselben Templates mit anderen Werten gerendert werden. Leg eine zweite Werte-Datei für die Produktion an. Sie enthält nur die Abweichungen von der values.yaml:

    recipes-db/values-prod.yaml:

    image:
  tag: "17"
replicas: 3
database:
  name: recipes_prod

    Rendere das Chart einmal mit den Standardwerten und einmal mit der Datei für die Produktion, und vergleiche die Ausgaben:

    helm template test-release ./recipes-db

    helm template test-release ./recipes-db -f ./recipes-db/values-prod.yaml

    Die mit -f übergebene Datei überschreibt nur die Werte, die darin stehen; alles andere kommt weiter aus der values.yaml. So erzeugt ein Chart je Umgebung andere Manifeste: anderes Image-Tag, mehr Replicas, anderer Datenbankname.

    Hinweis: Beim Installieren funktioniert das genauso: helm install recipes-db ./recipes-db -f ./recipes-db/values-prod.yaml. Installiert wird hier aber mit den Standardwerten.

    Die Datenbank mit Helm installieren

    helm install recipes-db ./recipes-db

    Beobachte den Start (Beenden mit Strg+C):

    oc get pods -w

    Sieh Dir das Release an:

    helm list

    helm status recipes-db

    Prüf in den Logs, ob das Init-SQL gelaufen ist:

    oc logs deployment/postgres
