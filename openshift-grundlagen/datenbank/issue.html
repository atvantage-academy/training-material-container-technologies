    Eine PostgreSQL-Datenbank bereitstellen

    User Story

    Als Entwickler:in möchte ich eine PostgreSQL-Datenbank in OpenShift betreiben, deren Konfiguration sauber und sicher bereitgestellt wird, damit das Backend später auf eine echte Datenbank umgestellt werden kann.

    Lernziele
    • Du betreibst eine Datenbank als Workload im Cluster.
    • Du stellst die Konfiguration einer Anwendung von außen bereit – getrennt nach sensiblen und nicht sensiblen Werten.
    • Du bringst eine Datei in einen Container, die nicht Teil des Images ist.
    • Du erklärst, warum ein Container unter OpenShift mit einer beliebigen User-ID zurechtkommen muss.
    Definition of Done
    • Ein PostgreSQL-Pod läuft mit den geforderten Parametern und steht auf Running.
    • Die Zugangsdaten kommen aus einem Secret; das Deployment-Manifest verweist nur darauf.
    • Der Datenbankname kommt aus einer ConfigMap.
    • Die Logs zeigen, dass init.sql beim ersten Start ausgeführt wurde.
    • PostgreSQL schreibt in ein eigenes Datenverzeichnis (PGDATA) auf einem Volume.
    • Du hast die Kontrollfragen beantwortet

    Aufgabe

    Diese Übung beschreibt nur das Ziel und die Parameter – nicht den Weg. Überleg selbst, mit welchen Ressourcen Du das umsetzt. Alles, was Du dafür brauchst, kennst Du aus den bisherigen Übungen oder findest es in den Links unter „Selbstlernmaterial“ und mit oc explain.

    Benötigt wird ein Pod mit einer PostgreSQL-Datenbank, der diese Parameter erfüllt:

    Parameter Wert
    Image postgres:17-alpine
    Port 5432
    POSTGRES_USER (Umgebungsvariable) frei wählbar, zum Beispiel recipes
    POSTGRES_PASSWORD (Umgebungsvariable) frei wählbar, zum Beispiel recipes-secret-pw
    POSTGRES_DB (Umgebungsvariable) recipes
    Init-SQL Datei init.sql im Verzeichnis /docker-entrypoint-initdb.d/

    Dabei gilt:

    • Die Zugangsdaten (POSTGRES_USER, POSTGRES_PASSWORD) stehen nicht im Klartext im Deployment.
    • Der Datenbankname (POSTGRES_DB) ist unkritisch, soll aber ebenfalls von außen konfigurierbar sein.
    • Nenne das Deployment postgres und gib ihm das Label app: postgres – die nächsten Übungen bauen darauf auf.

    Das Init-SQL, das beim ersten Start das Schema anlegt:

    CREATE TABLE recipes (
    id          VARCHAR(36)   PRIMARY KEY,
    name        VARCHAR(100)  NOT NULL,
    img         VARCHAR(255),
    servings    INTEGER       NOT NULL,
    lastEdited  TIMESTAMP WITH TIME ZONE,
    duration    INTEGER       NOT NULL,
    difficulty  VARCHAR(10),
    preparation VARCHAR(2000) NOT NULL
);

CREATE TABLE ingredients (
    id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name      VARCHAR(100) NOT NULL,
    quantity  DOUBLE PRECISION NOT NULL,
    unit      VARCHAR(20)  NOT NULL,
    recipe_id VARCHAR(36)  REFERENCES recipes(id) ON DELETE CASCADE
);

    Arbeitsschritte

    Die Ressourcen anlegen

    Leg die Ressourcen an, die die Aufgabe verlangt, und das Deployment der Datenbank. Zwei Hinweise helfen Dir dabei:

    Das Init-SQL in den Container bringen. Das offizielle PostgreSQL-Image führt beim ersten Start alle *.sql-Dateien aus /docker-entrypoint-initdb.d/ aus. Eine Datei, die nicht im Image liegt, legst Du als ConfigMap an und hängst sie als Volume ein. Das Muster, abstrakt:

    # Ausschnitt aus einem Pod- bzw. Deployment-Template
spec:
  containers:
    - name: my-app
      image: my-image
      volumeMounts:
        - name: my-files
          mountPath: /pfad/im/container
  volumes:
    - name: my-files
      configMap:
        name: meine-configmap

    Kein persistenter Speicher nötig. Für diese Übung genügt flüchtiger Speicher. Produktionsreif wäre ein StatefulSet mit PersistentVolumeClaim – siehe PostgreSQL auf Kubernetes.

    Den Zwischenstand prüfen

    Wende Deine Ressourcen an und sieh Dir Status und Logs des Pods an:

    oc get pods

    oc logs <postgres-pod-name>

    Der Pod wird noch nicht sauber starten. In den Logs steht ein Fehler beim Anlegen des Datenverzeichnisses:

    fixing permissions on existing directory /var/lib/postgresql/data ... initdb: error: could not change permissions of directory "/var/lib/postgresql/data": Operation not permitted

    Die Ursache: OpenShift startet den Container mit einer zufällig vergebenen User-ID (Security Context Constraint). Dieser User-ID gehört das Standard-Datenverzeichnis /var/lib/postgresql/data nicht, und PostgreSQL darf dessen Rechte nicht ändern.

    Hinweis: Welche User-ID Dein Pod bekommen hat, steht in seiner Beschreibung – such in der Ausgabe nach runAsUser:

    oc get pod <postgres-pod-name> -o yaml

    PostgreSQL ein eigenes Datenverzeichnis geben

    Behebe den Fehler, indem PostgreSQL ein eigenes, beschreibbares Datenverzeichnis bekommt. Ergänze im Deployment drei Dinge:

    1. die Umgebungsvariable PGDATA auf ein Unterverzeichnis,
    2. einen volumeMount für die Daten,
    3. das zugehörige volume – hier emptyDir, flüchtig und für diese Übung ausreichend.
        spec:
      containers:
        - name: postgres
          image: postgres:17-alpine
          # Ports, envFrom (Secret und ConfigMap) und das Init-SQL wie zuvor …
          env:
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
      volumes:
        - name: data
          emptyDir: {}

    Warum das hilft: Das leere, beschreibbare Volume data liegt auf /var/lib/postgresql/data. Mit PGDATA=/var/lib/postgresql/data/pgdata legt PostgreSQL sein Datenverzeichnis in ein selbst angelegtes Unterverzeichnis – das gehört ihm, und dessen Rechte darf es setzen.

    Wende das Deployment erneut an:

    oc apply -f postgres-deployment.yaml

    oc get pods

    oc logs <postgres-pod-name>

    Jetzt läuft der Pod, und in den Logs siehst Du, wie init.sql ausgeführt wird.

    Die Tabellen prüfen

    Frag die Datenbank im Container nach ihren Tabellen:

    oc exec deployment/postgres -- psql -U recipes -d recipes -c '\dt'

    Hinweis: Hast Du einen anderen Benutzer gewählt, setz ihn hinter -U ein.

    Musterlösung

    Musterlösung aufdecken – erst, wenn Du es selbst versucht hast

    Eine mögliche, vollständige Lösung – als YAML und als Befehle. Andere Wege sind genauso gültig, solange die Parameter erfüllt sind.

    Secret mit den Zugangsdaten

    Deklarativ, als Datei postgres-secret.yaml:

    apiVersion: v1
kind: Secret
metadata:
  name: postgres-secret
type: Opaque
stringData:
  POSTGRES_USER: recipes
  POSTGRES_PASSWORD: recipes-secret-pw

    oc apply -f postgres-secret.yaml

    stringData nimmt Klartext entgegen; Kubernetes kodiert ihn selbst in Base64. Unter data müsstest Du die Werte selbst kodieren.

    Oder per Befehl:

    oc create secret generic postgres-secret --from-literal=POSTGRES_USER=recipes --from-literal=POSTGRES_PASSWORD=recipes-secret-pw

    Noch sauberer: ein Zufallspasswort. Dann steht das Passwort in keiner Datei. Da es nur über das Secret referenziert wird, muss es niemand kennen:

    # 32 zufällige Zeichen aus 0–9 und a–f
PW=$(openssl rand -hex 16)

    oc create secret generic postgres-secret --from-literal=POSTGRES_USER=recipes --from-literal=POSTGRES_PASSWORD="$PW"

    Hinweis: Base64 ist keine Verschlüsselung. Wer das Secret lesen darf, sieht die Werte im Klartext:

    oc extract secret/postgres-secret --to=-

    ConfigMap mit dem Datenbanknamen

    Als Datei postgres-config.yaml:

    apiVersion: v1
kind: ConfigMap
metadata:
  name: postgres-config
data:
  POSTGRES_DB: recipes

    oc apply -f postgres-config.yaml

    Oder per Befehl:

    oc create configmap postgres-config --from-literal=POSTGRES_DB=recipes

    ConfigMap mit dem Init-SQL

    Am einfachsten aus der Datei init.sql:

    oc create configmap postgres-init-sql --from-file=init.sql

    Oder deklarativ mit eingebettetem Inhalt, als Datei postgres-init-sql.yaml:

    apiVersion: v1
kind: ConfigMap
metadata:
  name: postgres-init-sql
data:
  init.sql: |
    CREATE TABLE recipes (
        id          VARCHAR(36)   PRIMARY KEY,
        name        VARCHAR(100)  NOT NULL,
        img         VARCHAR(255),
        servings    INTEGER       NOT NULL,
        lastEdited  TIMESTAMP WITH TIME ZONE,
        duration    INTEGER       NOT NULL,
        difficulty  VARCHAR(10),
        preparation VARCHAR(2000) NOT NULL
    );

    CREATE TABLE ingredients (
        id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
        name      VARCHAR(100) NOT NULL,
        quantity  DOUBLE PRECISION NOT NULL,
        unit      VARCHAR(20)  NOT NULL,
        recipe_id VARCHAR(36)  REFERENCES recipes(id) ON DELETE CASCADE
    );

    oc apply -f postgres-init-sql.yaml

    Deployment

    Als Datei postgres-deployment.yaml:

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres
spec:
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:17-alpine
          ports:
            - containerPort: 5432
          env:
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          envFrom:
            - secretRef:
                name: postgres-secret
            - configMapRef:
                name: postgres-config
          volumeMounts:
            - name: init-sql
              mountPath: /docker-entrypoint-initdb.d
            - name: data
              mountPath: /var/lib/postgresql/data
      volumes:
        - name: init-sql
          configMap:
            name: postgres-init-sql
        - name: data
          emptyDir: {}

    oc apply -f postgres-deployment.yaml

    Worauf es ankommt:

    • envFrom übernimmt alle Schlüssel aus Secret und ConfigMap als Umgebungsvariablen (POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB). Einzeln geht es mit env und valueFrom.secretKeyRef – das brauchst Du in der nächsten Übung.
    • Das Volume init-sql liegt unter /docker-entrypoint-initdb.d. Das offizielle Image führt die *.sql-Dateien nur beim ersten Start aus, solange das Datenverzeichnis leer ist.
    • PGDATA und das Volume data: Ohne sie scheitert der Start auf OpenShift, weil die zufällig vergebene User-ID /var/lib/postgresql/data nicht anpassen darf. Das emptyDir ist beschreibbar, PGDATA legt die Daten in ein selbst angelegtes Unterverzeichnis.

    Prüfen

    oc get pods

    # Wurde das Init-SQL ausgeführt?
oc logs deployment/postgres

    # Gegenprobe in der Datenbank
oc exec deployment/postgres -- psql -U recipes -d recipes -c '\dt'

    Nachtrag: emptyDir und der Weg zur Persistenz

    Ein emptyDir ist ein leeres Verzeichnis auf dem Node, auf dem der Pod läuft. Es lebt so lange wie der Pod: Ein Neustart des Containers behält die Daten, beim Löschen oder Umziehen des Pods sind sie weg. Es ist also kein persistenter Speicher.

    PGDATA auf einem Unterverzeichnis hilft in zwei Fällen: auf OpenShift wegen der zufälligen User-ID – und bei manchen PersistentVolumes, deren Wurzel nicht leer ist (etwa mit einem Ordner lost+found). In der Übung „Persistenten Speicher einrichten“ wird das emptyDir durch einen PersistentVolumeClaim ersetzt; volumeMount und PGDATA bleiben, wie sie sind.

    Reflexionsfragen

    • Wie hast Du dafür gesorgt, dass die Zugangsdaten nicht im Klartext im Deployment stehen? Welche Ressource ist dafür gedacht?
    • Warum gehören Datenbankname und Zugangsdaten in unterschiedliche Ressourcentypen?
    • Wie sicher ist ein Secret wirklich?
    • Warum bindest Du das Init-SQL von außen ein, statt es ins Image zu packen?
    • Was unterscheidet envFrom (ganze Ressource) von einzelnen env-Einträgen mit valueFrom?
    • Warum startete PostgreSQL zuerst nicht, und warum hilft ein eigenes Datenverzeichnis?
    • Was ist an diesem Aufbau noch nicht produktionsreif?
